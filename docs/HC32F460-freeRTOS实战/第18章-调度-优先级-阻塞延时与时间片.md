# 第 18 章 调度:优先级、阻塞延时与时间片

上一章讲了任务由"栈 + TCB"构成。那么谁来把 CPU 分给这些任务?答案就是**调度器**。这一章讲清调度器的三件事:**它凭什么决定谁先跑(优先级)、任务睡着的时候内核在干什么(延时列表)、同优先级怎么分(时间片)**。

---

## 18.1 调度器要解决的核心问题

任意时刻,如果同时有多个任务处于"就绪"态,**下一个该运行谁?**

FreeRTOS 给出的答案是**优先级**:永远让"当前就绪的最高优先级任务"运行。调度器就是在每次需要决策时,找到那个任务并切换过去。

需要决策的时刻就是上一章说的三种:

1. tick 中断到来;
2. 某个任务自己阻塞(延时/等队列);
3. 中断里唤醒了更高优先级的任务。

---

## 18.2 优先级与抢占:就绪列表是怎么组织的

### 18.2.1 就绪列表的结构

内核为**每一个优先级**维护一条就绪任务链表。本工程 `configMAX_PRIORITIES = 7`,就有 7 条链表(优先级 0~6)。

调度时内核做的事,概念上就是:

```
从最高优先级(6)往下扫,找到第一条非空的就绪链表,取它的队首任务来运行
```

所以"抢占"的实现非常直白:**只要有一个更高优先级的任务进入就绪态,调度器立刻发现"更高优先级的链表非空了",于是马上切换过去**,当前任务被剥夺 CPU(它自己还保持在就绪态,等下次轮到)。

### 18.2.2 本工程的优先级分配

| 任务 | 优先级 | 为什么这么定 |
|------|--------|-------------|
| ConsoleShell / KEY | 2 | 串口字符/按键要尽快响应,否则跟手感差 → 高点 |
| LED / GUI / NvStore | 1 | 慢节奏的周期性/界面/落盘任务 → 低点 |
| ConsoleOut | 空闲+1 | 异步打印,CPU 空闲时才发串口 → 更低 |
| TimeInit / 空闲任务 | 0 | 初始化线程跑完自删;空闲任务内核自动创建,永远最低 |

**重点提醒**:任务优先级是**数值越大越高**。而 Cortex-M 的 NVIC 中断优先级是**数值越小越高**——两者方向相反,这是初学者最高频的出错点,第 19 章会再强调一次。

### 18.2.3 优先级别乱设

把任务优先级设高的代价是:**它会抢占一切比它低的任务**,而且只要它不阻塞,低优先级任务就永远别想跑。所以:

- 只有"真的不能等"的任务(如收串口字节、采集关键信号)才设高;
- **不要把所有任务都设为最高优先级**——那等于没分优先级,退化成时间片轮转,还白白丧失了抢占的意义;
- 大多数周期性任务给同一个较低优先级,靠时间片轮转即可。

## 18.3 阻塞延时是怎么实现的:延时列表

这是本章最值得理解的**原理**——它解释了"为什么 RTOS 能高效管理成百上千个正在延时的任务"。

### 18.3.1 朴素做法为什么不行

最直觉的做法:每个任务在自己的 TCB 里记一个"剩余 tick 数",每个 tick 中断把所有任务的剩余数都减 1,减到 0 就唤醒。

问题是这是 **O(n)**:任务越多,每个 tick 要遍历的任务越多。tick 是 1ms 一次的高频中断,在这个中断里遍历所有任务是不可接受的。

### 18.3.2 FreeRTOS 的做法:延时列表 + 有序插入

FreeRTOS 换了个思路:

1. 内核维护一个全局计数器 `xTickCount`,每 tick 加 1。
2. 任务调用 `vTaskDelay(n)` 时,内核计算它的**唤醒时刻** `= xTickCount + n`,然后把它按唤醒时刻**从小到大排序**挂进"延时列表"。
3. 每个 tick 中断,内核**只需要看延时列表的队首**:如果队首任务的唤醒时刻 ≤ 当前 tick 了,就把它取出来放回就绪列表;否则后面的一定都还没到,直接结束。

因为列表是有序的,**每 tick 的检查是 O(1)**,与任务总数无关。延时中的任务越多,这个设计的优势越大。

> 这就是"任务延时列表"存在的意义。理解了它,你也就理解了为什么 `vTaskDelay` 的精度是 **±1 个 tick**——唤醒只在 tick 中断里检查,而调用时刻可能落在两个 tick 之间。

### 18.3.3 tick 频率怎么选

`configTICK_RATE_HZ` 决定 tick 周期,本工程设为 1000,即 **1ms 一个 tick**:

- **太快**(如 10kHz):tick 中断本身占用大量 CPU,浪费;
- **太慢**(如 10Hz):延时精度和任务响应都变粗糙;
- **1000Hz 是 MCU 上的常见折中**,既能毫秒级响应,开销也才千分之几。

## 18.4 空闲任务:为什么必须存在

考虑一个场景:**所有任务都阻塞了**(比如都在等延时)。此时 CPU 该干什么?

答案是:内核在启动调度器时会**自动创建一个优先级为 0 的空闲任务(Idle Task)**,它的函数体就是一个空转的死循环。这样:

1. **永远保证"至少有一个可运行的任务"**,调度器逻辑得以简化(不用处理"没有任务可跑"的特殊分支);
2. **回收被删除任务的内存**:`vTaskDelete` 删除的任务,其栈和 TCB 由空闲任务负责释放;
3. **低功耗的落脚点**:可以在空闲任务里让 CPU 进入休眠(Tickless 模式就是在空闲时关掉 tick 并休眠)。本工程未使用,仅作了解。

> 空闲任务钩子 `vApplicationIdleHook` 允许你在空闲时插自己的代码(常用于统计 CPU 利用率),本工程未启用。

## 18.5 时间片:同优先级怎么分 CPU

### 18.5.1 问题

两个同优先级的任务(本工程 LED 和 GUI 都是优先级 1)都就绪时,谁先跑?如果让先就绪的那个一直跑到阻塞为止,另一个就可能长时间得不到 CPU。

### 18.5.2 时间片轮转

FreeRTOS 的做法是**时间片(Time Slice)**:同优先级的多个就绪任务,**每个 tick 轮流**——当前任务用完一个 tick 后,如果同优先级还有别的就绪任务,就切换到队尾的下一个。

于是本工程的 LED 与 GUI 就这样"你 1ms、我 1ms"地交替推进,谁都不会被饿死。

### 18.5.3 要点

- 时间片**只在同优先级任务之间**生效;不同优先级之间靠的是**抢占**,不是时间片。
- 时间片长度 = 1 个 tick(本工程 1ms),由 `configUSE_TIME_SLICING` 控制(默认开启)。
- 时间片轮转的前提是任务会**阻塞或让出**;如果同优先级任务里有死循环忙等的,时间片也救不了它(它虽然会被切走,但会一直占着就绪态反复抢 CPU)。

## 18.6 vTaskDelay 与 vTaskDelayUntil:原理与取舍

这是延时 API 里最容易选错的一对,理解了原理就不会选错。

### 18.6.1 vTaskDelay:相对延时

```c
for (;;) {
    do_work();                        /* 任务体,耗时不固定 */
    vTaskDelay(pdMS_TO_TICKS(100));   /* 从"调用这一刻"起睡 100ms */
}
```

它是**从调用时刻开始计时**的。但 `do_work()` 本身要花时间,期间任务还可能被更高优先级任务抢占。所以实际周期是:

```
实际周期 = do_work() 耗时 + 被抢占的时间 + 100ms
```

**周期不严格**,会随负载漂移。

### 18.6.2 vTaskDelayUntil:绝对延时

```c
TickType_t xLastWakeTime = xTaskGetTickCount();
for (;;) {
    do_work();
    vTaskDelayUntil(&xLastWakeTime, pdMS_TO_TICKS(100));  /* 以"上次唤醒时刻"为基准推进 */
}
```

它记录"上次唤醒的时刻",每次把基准**往前推 100ms**,然后睡到那个绝对时刻。这样 `do_work()` 的耗时和被抢占的时间都被**补偿掉**了,得到**严格固定**的周期。

### 18.6.3 怎么选

| 场景 | 用哪个 | 理由 |
|------|--------|------|
| 闪灯、轮询按键、一般心跳 | `vTaskDelay` | 差几毫秒无所谓,写法简单 |
| 定时采样(如每 10ms 采一次 ADC)、控制环 | `vTaskDelayUntil` | 周期必须准,不能随负载漂移 |
| 本工程 `vLedTask`(500ms 一拍,两拍累加 `g_u32Sec` 走一秒) | `vTaskDelay(500)` | 走秒差几毫秒看不出来,够用 |

> 注意:这两种延时的**精度都是 ±1 个 tick**(唤醒只在 tick 中断里发生)。如果需要比 tick 更精细的定时,应该考虑用硬件定时器,而不是调高 tick 频率。

---

## 18.7 小结

- 调度器的判据是**优先级**:永远运行"就绪的最高优先级任务",高优先级进入就绪即**抢占**。
- 任务优先级**数值越大越高**,与 NVIC 中断优先级方向**相反**。
- 阻塞延时靠**延时列表 + 有序插入**实现,每 tick 只检查队首,是 O(1) 的;`vTaskDelay` 精度为 **±1 tick**。
- **空闲任务**(优先级 0)保证永远有任务可跑,并负责回收被删除任务的内存。
- **时间片**解决同优先级任务的轮转,只在同优先级间生效。
- `vTaskDelay` 是相对延时(周期会被拉长),`vTaskDelayUntil` 是绝对延时(补偿耗时,周期严格);按"周期要不要准"来选。
