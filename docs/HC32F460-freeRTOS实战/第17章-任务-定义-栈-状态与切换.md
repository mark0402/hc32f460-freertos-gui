# 第 17 章 任务:定义、栈、状态与切换

上一章我们得出一个结论:RTOS 把并发活动拆成多个任务。这一章把"任务"彻底拆开——**它到底是什么、由什么构成、在内核眼里长什么样、切换时 CPU 干了什么**。

理解这一章,后面所有跟任务相关的 API(`xTaskCreate`、`vTaskDelay`、`vTaskSuspend` …)对你来说就不再是"抄参数",而是"我知道它背后动了什么"。

---

## 17.1 任务的本质

从代码上看,任务就是一个函数:

```c
static void vLedTask(void *pvParameters)
{
    (void)pvParameters;
    for (;;) {
        PORT_Toggle(GPIO_OUT_PORT, GPIO_OUT_PIN);
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
```

但**任务 ≠ 普通函数**。普通函数被调用时用的是调用者的栈、跑完就返回;任务则被内核额外"装备"了两样东西:

- **一块私有栈**:任务自己专用的内存区域,存放它的局部变量和函数调用链。
- **一个任务控制块(TCB)**:内核用来登记这个任务的内部数据结构。

打个比方:函数是**菜谱**,任务是**一个正在按菜谱做菜的厨师**——他有自己的案板(栈),有自己的工牌(TCB),调度器是车间主任,决定此刻让哪个厨师上灶。

所以"创建一个任务"的真正在发生的事是:

1. 从内核堆里**分配一块栈内存**;
2. **初始化一个 TCB**(记录栈顶、优先级、状态、名字等);
3. 把任务**挂进就绪列表**,交给调度器管理。

---

## 17.2 为什么每个任务必须有独立的栈

这是理解任务的关键,也是最容易出事故的地方。

### 17.2.1 栈里放的是什么

函数被调用时,CPU 需要一块内存存放:

- 函数的**局部变量**;
- **函数调用链**(返回地址、上一层函数的现场);
- 发生中断/切换时的**寄存器现场**。

这块内存就是栈。同一时刻 CPU 的栈指针(SP)只有一个。

### 17.2.2 共用一块栈会怎样

假设两个任务共用栈:A 任务执行到 `FuncA() → FuncB()` 一半,正在等延时被切走,栈里留着 A 的调用现场;紧接着 B 开始运行,它也往下压栈——**B 的数据直接盖在 A 的现场上**。等 A 被唤醒恢复时,栈顶已经不是它的东西了,程序立刻跑飞。

所以:**每个任务必须有一块自己的栈。** 切换任务时,内核只需要保存/恢复 CPU 寄存器、并把栈指针(SP)指向新任务的栈,各任务的调用现场自然就互不干扰。

### 17.2.3 栈大小怎么定,给小了会怎样

栈大小在创建任务时指定,**单位是"字"(Word),不是字节**——在 HC32F460(Cortex-M4)上 1 字 = 4 字节。所以 `configMINIMAL_STACK_SIZE = 128` 实际是 **512 字节**,不是 128 字节。这是初学者最常踩的坑之一。

估算原则:

```
所需栈 ≈ 最深函数调用链 × 每层开销 + 最大的局部数组 + 中断嵌套余量 + 安全余量
```

给少了的后果是**栈溢出 → 踩到别的内存 → HardFault**,表现为"跑着跑着莫名其妙死机",而且极难定位。本工程给调用链很深的 GUI 任务额外加了 512 字,就是这个原因(第 27 章会再提)。

> 实践建议:初版先给保守一点,跑通后用 `uxTaskGetStackHighWaterMark()` 看实际用了多少,再往回收。

## 17.3 任务控制块 TCB:内核眼里的任务

内核用 TCB(Task Control Block)描述一个任务。你不需要去改它,但要知道它记录了什么:

| TCB 中的关键字段 | 作用 |
|---|---|
| 栈顶指针 | 切换时恢复现场用 |
| 任务状态 | 运行/就绪/阻塞/挂起 |
| 优先级 | 调度决策的依据 |
| 任务名 | 仅调试用 |
| 各类链表节点 | 把任务挂进就绪列表、延时列表、事件等待列表 |

**理解 TCB 的意义在于**:所谓"任务管理",本质上就是内核在操作这些 TCB 和它们所在的链表。比如 `vTaskDelay(500)` 做的事,就是把当前任务的 TCB 从就绪列表摘下来、挂到延时列表上去(第 18 章展开)。

## 17.4 任务的四种状态与迁移

任务在生命周期里处于四种状态之一:

| 状态 | 含义 | 占 CPU 吗 |
|------|------|----------|
| **运行(Running)** | 正占用 CPU | 是 |
| **就绪(Ready)** | 能跑,在等 CPU | 不占,但随时可上 |
| **阻塞(Blocked)** | 在等某个事件(延时到 / 队列来数据 / 信号量释放) | **不占** |
| **挂起(Suspended)** | 被 `vTaskSuspend` 冻住,不参与调度 | 不占 |

状态迁移关系:

```
   创建任务 ──> 就绪
      就绪  ──(被调度)──> 运行
      运行  ──(被更高优先级抢占 / 时间片到)──> 就绪
      运行  ──(vTaskDelay / 等队列 / 等信号量)──> 阻塞
      阻塞  ──(延时到 / 收到数据 / 信号量释放)──> 就绪
      任意  ──(vTaskSuspend)──> 挂起
      挂起  ──(vTaskResume)──>  就绪
```

**要点**:

- 只有"就绪"和"运行"的任务参与抢 CPU;**阻塞态的任务不占 CPU**,这是 RTOS 效率的关键。
- 阻塞是**任务自愿让权**(我要等个事),挂起是**外部强制冻结**(你先别跑)。
- 阻塞到期是"回到就绪",不是"立刻运行"——还要等调度器轮到它。

## 17.5 任务切换时,CPU 到底做了什么

### 17.5.1 什么时候会切换

三种触发时机:

1. **tick 中断里发现该切了**:比如同优先级任务时间片到了,或有更高优先级任务被唤醒。
2. **任务自己让权**:调用 `vTaskDelay`、等队列/信号量而阻塞。
3. **中断里唤醒了更高优先级任务**:比如 ISR 发了个队列,唤醒了等待它的高优先级任务。

### 17.5.2 为什么切换放在 PendSV

在 Cortex-M 上,真正的上下文切换**并不在 SysTick 中断里做**,而是"挂起"一个 **PendSV 异常**来完成。原因是:PendSV 被设为**最低优先级**,这样高优先级的中断都能先正常返回,切换被推迟到所有中断都处理完之后才执行——保证了中断响应的及时性,也避免了在中断中途切换导致现场混乱。

(所以第 21 章移植时你会看到三个内核异常 `SVC` / `PendSV` / `SysTick` 都要接好,这不是玄学,是这套机制的要求。)

### 17.5.3 "上下文"是什么

上下文就是**CPU 寄存器现场**:R0–R15、xPSR 等。任务被切走时,内核把这些寄存器压入**该任务自己的栈**;任务被恢复时,从它自己的栈里弹出,重新装回 CPU 寄存器,并让 SP 指向它的栈。

于是从任务的视角看,它"什么都没发生过",接着上次的断点继续跑。

### 17.5.4 切换的代价

一次上下文切换的开销,就是**保存/恢复十几个寄存器**。正因为这么轻,1ms 级(甚至更快)的切换频率才是可行的。这也是 RTOS 能在几十 MHz 的 MCU 上跑起来的原因。

## 17.6 实践三问

### 17.6.1 为什么要创建任务

因为**每创建一个任务,就是向内核申报一个"可独立调度的执行流"**,让一个并发活动(闪灯、收串口、刷屏)拥有自己的栈和优先级,可以被独立地暂停、恢复、等待事件。

带来的直接好处:每个任务的逻辑可以写成**简单的顺序程序**("干完 → 等一会儿 → 再干"),而不用写成"检查时间戳 → 看要不要动 → 立刻返回"的状态机。复杂性从你的代码转移到了调度器。

### 17.6.2 创建任务要注意什么(规则清单)

1. **必须 `for(;;)`,绝不能 `return`**:任务没有合法的"返回地址",return 会直接跑飞。要结束自己用 `vTaskDelete(NULL)`。
2. **阻塞,不要忙等**:用 `vTaskDelay` / 等队列 / 等信号量让出 CPU;写成 `while(flag);` 会让 RTOS 退化成裸机,同优先级任务全部饿死。
3. **栈深度单位是"字"**:按"最深调用链 + 最大局部数组 + 余量"估算,宁可先给大一点。栈溢出 = HardFault。
4. **优先级别拍脑袋**:数值越大优先级越高(和 NVIC 中断优先级"数值越小越高"**相反**,别混)。把真正"不能丢"的(如串口收数)设高;**别把所有任务都设成最高优先级**,那等于没分优先级。
5. **共享数据要守纪律**:跨任务访问同一份数据,要么用队列/信号量这类线程安全原语,要么用"一个写、一个读"的全局变量并明确所有权。裸写全局变量会出竞态。
6. **名字与句柄**:任务名仅用于调试(长度受 `configMAX_TASK_NAME_LEN` 限制);`TaskHandle_t` 句柄用于后续删除/挂起/改优先级,用不到就填 `NULL`。

### 17.6.3 任务代码放在哪里比较好

原则:**按功能模块组织,而不是按 RTOS 组织**。反面教材是把所有任务逻辑全塞进 `main.c`,或让任务函数直接去操作外设寄存器——结果是业务逻辑和 RTOS 绑死,换内核或做单元测试时处处要改。

本工程采用的分层:

```
main.c          硬件初始化 + MX_FREERTOS_Init()(集中建任务) + vTaskStartScheduler()
   │
RTOSThread.c    集中建任务入口 MX_FREERTOS_Init()(任务壳分散在各模块)
   │              例:vLedTask 在 bsp_led.c:「读 g_u8LedMode → 翻转/置位 → vTaskDelay」
   ▼
业务/驱动层     真正的逻辑下沉到这里,与 OS 无关:
   console.c    统一控制台:串口收发 + ring buffer + 命令解析与分发
   gui.c        界面展示(时钟只读取,推进归硬件 RTC)
   bsp_key.c    按键采集 + 事件队列(BSP)
   bsp_led.c    三色 LED 驱动 + 心跳任务(BSP)
```

要点是**任务函数要保持"薄"**——它只负责三件事:**循环、调用、阻塞**。这样做的好处:

- 任务壳一眼能看懂"这个任务在干什么";
- 业务逻辑与 RTOS 解耦,可在无 RTOS 环境下单独测试;
- 将来换 RTOS,只改 `RTOSThread.c` 这一层壳。

你自己的工程也建议照这个模式:任务壳集中放,业务下沉成模块,任务之间**只通过接口或队列说话**。

---

## 17.7 小结

- 任务 = 一个永不返回的 `for(;;)` 函数 + **一块私有栈** + **一个 TCB**;创建任务的本质是分配栈、初始化 TCB、挂进就绪列表。
- **每个任务必须有独立栈**,否则调用现场会被别的任务覆盖;栈大小单位是**字**,给小了会 HardFault。
- 任务有**运行/就绪/阻塞/挂起**四态,只有就绪和运行参与抢 CPU;**阻塞不占 CPU** 是 RTOS 效率的关键。
- 上下文切换由 **PendSV** 完成(而非 SysTick 里直接切),开销就是保存/恢复寄存器,所以毫秒级切换可行。
- 任务函数要**薄**(循环/调用/阻塞),业务逻辑下沉到独立模块。

**下一章**讲调度器:它凭什么决定谁先跑——优先级、抢占、阻塞延时是怎么实现的、时间片又是怎么回事。
