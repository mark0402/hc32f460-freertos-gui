# 第 19 章 临界段与中断管理

原理篇最后一章,解决两个和"并发正确性"直接相关的问题:

1. 多个任务(以及中断)同时碰同一份数据时,怎么保证不出错——**临界段**;
2. 硬件事件通过中断来了以后,怎么安全地把它交给任务处理——**中断管理**。

这一章讲清那条著名的铁律"**中断里只能用 `FromISR` 版 API**"到底为什么存在,而不是让你死记。

---

## 19.1 临界段:为什么需要它

### 19.1.1 一个具体的竞态例子

假设 `g_u32Sec` 被两个地方访问:LED 任务每约 1 秒 `g_u32Sec++`,串口命令 `uptime` 读它打印。

`g_u32Sec++` 看起来是一句,在 CPU 里其实是**三步**:

```
① 从内存读 g_u32Sec 到寄存器
② 寄存器加 1
③ 写回内存
```

如果 LED 任务刚执行完 ②,还没来得及 ③,就被更高优先级的 ConsoleShell 任务抢占,而 `uptime` 命令正好读 `g_u32Sec`——**它读到的是"加了但还没写回"的旧值**。这就是**竞态(Race Condition)**。

更糟的是,如果两边都是"写"(比如两个任务都做 `++`),那某一次自增就可能彻底丢失。

### 19.1.2 临界段的定义

**临界段(Critical Section)**就是"必须一口气执行完、中途不允许被打断"的代码段。上面的 ①②③ 就构成一个临界段。

需要注意的是,"打断"有两个来源:

- **其它任务抢占**(只要调度器不切换就不会发生);
- **中断**(只有屏蔽中断才能挡住)。

对应到保护手段,就有三种,强度和代价各不相同。

---

## 19.2 三种保护手段与适用场景

| 手段 | API | 挡住了什么 | 适用场景 |
|------|-----|-----------|---------|
| **关中断** | `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()` | 挡住任务切换**和**部分中断 | 极短的临界段(几条指令、几微秒) |
| **挂起调度器** | `vTaskSuspendAll()` / `xTaskResumeAll()` | 只挡任务切换,**中断照常响应** | 稍长、但不希望被切走的段 |
| **互斥量** | `xSemaphoreCreateMutex()` / `xSemaphoreTake/Give` | 只挡"同样要拿这把锁"的任务 | 保护时间可能很长的共享资源(独占外设) |

### 19.2.1 关中断:最强,但要极短

关中断期间,系统的实时性被破坏——**所有被屏蔽的中断都得等着**。所以它只适合保护"几条指令"级别的极短临界段(比如改一个标志位、往环形缓冲写指针)。

### 19.2.2 挂起调度器:折中

只禁止任务切换,中断还能正常响应。适合"我要连着改好几个变量,但不希望中途被别的任务插一脚"的场景。

### 19.2.3 互斥量:保护长时间独占的资源

如果一个资源被占用的时间可能**很长**(比如往 LCD 刷一屏数据、操作 SPI Flash),用关中断是不可接受的(会长时间屏蔽中断),这时应该用**互斥量**:要用资源前"拿锁",用完"放锁",拿不到就阻塞等待。

互斥量还额外解决了**优先级继承**问题(避免低优先级任务占着锁、导致中优先级任务先跑、高优先级任务干等的"优先级反转"),这是关中断做不到的。第 25 章会展开。

> 本工程的情况:LCD 由 GUI 任务**独占**,没有争用,所以没上互斥量;全局变量 `g_u8LedMode`、`g_u32Sec` 则采用"**一个写、一个读**"的约定来规避竞态——这是最简单也最容易被忽视的纪律。

## 19.3 Cortex-M 的中断优先级机制

要理解 FreeRTOS 的中断规则,先得知道 Cortex-M 的中断优先级是怎么编的。

### 19.3.1 数值越小,优先级越高

NVIC 里,优先级数值 **0 最高,15 最低**(假设用 4 位表示)。这和任务优先级**完全相反**:

| | 数值大意味着 | 例 |
|---|---|---|
| **任务优先级** | 优先级**高** | ConsoleShell(2) > LED(1) |
| **中断优先级** | 优先级**低** | 优先级 2 的中断 > 优先级 5 的中断 |

**把这两套搞混,是初学者最高频的错误。** 再强调一次:任务优先级数大者高,中断优先级数小者高。

### 19.3.2 内核自己用哪个优先级

`configKERNEL_INTERRUPT_PRIORITY`(由 `configLIBRARY_LOWEST_INTERRUPT_PRIORITY`(本工程 = 15)左移得到)是内核给 `SVC`、`PendSV`、`SysTick` 这三个异常用的优先级,取**最低**。

这样做是为了保证:**任何用户中断都能抢占内核的 PendSV 切换操作**,中断响应不会被内核自身的活动拖慢。

---

## 19.4 FreeRTOS 的两条中断规则

`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`(本工程 = **5**)在中断优先级里划了一条线。它带来两条铁律:

### 规则一:优先级数值 < 5 的中断里,绝对不能调用任何 FreeRTOS API

(即优先级比 5 更高、数值更小的中断:0~4)

**为什么?** 因为内核保护临界段的方式,本质上是"**把中断屏蔽到某个优先级以下**"。也就是说,内核只能屏蔽"优先级数值 ≥ 5"的中断;**数值 < 5 的中断,内核根本管不着、屏蔽不掉**。

设想:内核正在修改就绪列表(改到一半,链表暂时处于不一致状态),此时一个优先级 3 的中断插进来,调用了 `xQueueSendFromISR`,它也会去动内核的链表——**在一个已经被改坏一半的链表上继续操作**,结果就是内存损坏、系统诡异崩溃。

所以这类中断里,**只能做纯硬件相关的事**(清中断标志、读写自己的缓冲区),**一个 FreeRTOS 函数都不能碰**。

### 规则二:优先级数值 ≥ 5 的中断里,只能调用带 `FromISR` 后缀的 API

例如 `xQueueSendFromISR`、`xSemaphoreGiveFromISR`、`xTaskNotifyFromISR`。普通版本(`xQueueSend` 等)**不能**在中断里用。

**为什么?** 见下一节。

### 规则三(补充):内核自身优先级必须最低

`configKERNEL_INTERRUPT_PRIORITY` 必须是最低优先级(数值最大),保证用户中断能随时抢占内核。

---

## 19.5 为什么中断里只能用 FromISR 版本

普通 API 和 `FromISR` API 的关键区别有两点:

### 19.5.1 FromISR 版永远不会阻塞

中断服务程序**不在调度器的管理之下**——它没有 TCB、不在任何就绪列表里。如果一个中断因为"队列满了要等"而阻塞,**没有任何机制能把它唤醒**,系统就死在那儿了。

所以 `FromISR` 版本的语义是:**能干就干,干不了立刻返回失败**,绝不等待。

### 19.5.2 FromISR 版用"标志位"代替"立即切换"

普通 API 在唤醒了更高优先级任务时会**立刻**触发上下文切换。但中断里不能说切就切(可能还有更高优先级的中断嵌套在处理中,直接切会乱套)。

`FromISR` 版改为:通过一个输出参数告诉你"我是否唤醒了更高优先级的任务":

```c
BaseType_t xHigherPriorityTaskWoken = pdFALSE;

xQueueSendFromISR(xQueue, &data, &xHigherPriorityTaskWoken);   /* 不会阻塞 */

/* 中断退出前:如果唤醒了更高优先级任务,请求一次切换 */
portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
```

`portYIELD_FROM_ISR` 并不会立刻切换,而是**挂起 PendSV**,把真正的切换推迟到所有中断都处理完之后(第 17 章讲过 PendSV 是故意设为最低优先级的)。这样既保证了切换的正确性,又不破坏中断的实时性。

**一句话记住**:中断里不能等、不能立刻切,所以要用 `FromISR` + `pxHigherPriorityTaskWoken` + `portYIELD_FROM_ISR` 这套组合。

---

## 19.6 延迟中断处理:工程上最重要的实践

理解了上面的规则,就得到一个非常重要的工程原则:**中断服务程序要快进快出,耗时的事情交给任务去做。**

这叫**延迟中断处理(Deferred Interrupt Processing)**。典型做法是:

```
ISR 里:清中断标志 + 把数据塞进缓冲区/发个信号   ← 极短
任务里:等信号 → 取出数据 → 做解析、处理、响应     ← 可长、可阻塞
```

### 本工程的两个实例

**实例一:串口接收**

```
USART 接收中断(ISR)      只做:读一个字节 → 塞进 ring buffer + give 信号量   ← 几微秒
ConsoleShell(任务)       做:取字符、回显、组行、交给 CLI 解析               ← 可以慢慢来
```

中断里绝不做"解析命令""回显字符串"这种耗时的事,否则会阻塞其它中断和所有任务。

**实例二:按键**

本工程的按键是**轮询任务**(`vKeyTask` 每 10ms 查一次引脚),而不是外部中断。这其实也是"延迟处理"思路的一种简化:把按键这种"人类速度"的事件交给任务轮询,既省了一个中断资源,逻辑也更简单(消抖、长短按判定都可以在任务里慢慢算)。

> 什么时候必须用中断?当事件**快到轮询来不及**(如高速通信、精确捕获)或对延迟极敏感时。人类按键(最快几十毫秒)用轮询完全够。

## 19.7 小结

- **临界段**是必须一口气执行完的代码;保护手段按强度递增为**关中断 → 挂起调度器 → 互斥量**,按临界段长短选择。
- 本工程对简单全局变量采用"**一个写、一个读**"的约定规避竞态;独占设备才需要互斥量。
- **任务优先级数值越大越高,中断优先级数值越小越高**,方向相反,别混。
- 中断铁律:优先级 **< 5** 绝不调任何 FreeRTOS API;**≥ 5** 只能调 `FromISR` 版,并配合 `portYIELD_FROM_ISR`。
- `FromISR` 之所以存在:中断**不能阻塞**(没人唤醒它)、**不能立即切换**(靠 PendSV 推迟)。
- 工程实践:**延迟中断处理**——ISR 只做最紧急的事,耗时逻辑交给任务。
