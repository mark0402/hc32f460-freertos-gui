# 第 22 章 创建任务:第一个多任务

内核已经跑起来了。本章把它变成**真正有用的多任务系统**:把裸机那个"闪灯 super-loop"拆成多个并行任务,并引出一个贯穿全书的原则——**任务壳只做"循环 + 调用 + 阻塞",业务下沉到独立模块**。

按应用篇的规矩,先把本章的**功能、用到的 API、为什么这么用**摆清楚:

| | 内容 |
|---|---|
| **本章功能** | 闪灯 + 系统走秒并行;顺带看清本工程真实的任务全景 |
| **用到的 API** | `xTaskCreate`、`vTaskDelay`、`pdMS_TO_TICKS`、`xTaskCreate` 的返回值 |
| **要解决的设计问题** | 拆成哪几个任务?栈给多大?优先级怎么定? |

---

## 22.1 设计:本工程真实的任务全景

回顾第 16、17 章:一个任务对应一个**并发活动**,拥有自己的栈和优先级。本工程(见 `RTOSThread.c` 的 `MX_FREERTOS_Init` 与 `main.c` 的 `Console_Init`)实际创建的任务如下:

| 任务 | 创建位置 | 优先级 | 职责 |
|------|----------|--------|------|
| `LED`(`vLedTask`) | `bsp_led_init()`(`bsp_led.c`) | 1 | 按模式驱动三色 LED(常亮/常灭/轮流闪),并每约 1s 累加 `g_u32Sec` |
| `ConsoleShell`(`prv_shell_task`) | `Console_Init()`(`console.c`) | 2 | 串口交互:行编辑、回显、组行、调 CLI 解析 |
| `ConsoleOut`(`prv_print_task`) | `Console_Init()`(`console.c`) | tskIDLE_PRIORITY+1 | 异步输出:从队列取日志/打印,用串口发出 |
| `KEY` | `bsp_key_init()`(`bsp_key.c`) | 2 | 按键扫描,事件入队(第 24 章) |
| `GUI` | `Gui_Start()` | 1 | 图形界面(第 28 章) |
| `TimeInit`(`vTimeInitTask`) | `MX_FREERTOS_Init` | 0 | 时间服务初始化线程,完成后自我删除 |
| `NvStore` | `NvStore_Init()`(`nv_store.c`) | 1 | 时间记录异步落盘,阻塞等保存队列 |

> 注意:**串口相关的任务不在 `RTOSThread.c` 里**,而是被收敛进统一的 `console` 组件(`console.c`)。本章先聚焦最典型、也最贴近"第一个多任务"的 **LED 任务**;串口命令行的完整实现留到第 27 章。

### 22.1.1 为什么"走秒"放在 LED 任务里,而不是单独建一个任务

裸机的 `while(1)` 里其实挤了好几件事。把它们各自解放成任务时,你可能会想:"闪灯一个任务、走秒一个任务"。本工程选择把 `g_u32Sec++` 直接并进 LED 任务的 500ms 循环里(每两拍 +1,即约 1s),**不单独建 `vUptimeTask`**。原因:

- 走秒对周期精度要求不高(差几毫秒看不出来),复用 LED 任务的节拍即可,**省一个任务、省一份栈**;
- 它和 LED 是同一节奏的慢周期活动,拆开反而增加任务切换与同步成本。

这一取舍体现了第 17 章的原则:**任务按"并发活动"划分,但不要为了"看起来整齐"而过度拆分**。后面"每秒严格走时 / 时间服务"这类更重的需求,才单独抽成 `TimeInit` 线程(第 26、28 章)。

## 22.2 动手:LED 任务

按第 17 章的分层原则,**任务壳放在 `bsp_led.c`**;真正的三色 LED 硬件操作下沉到 `gpio_out.c`(BSP 层)。GPIO 的配置细节见第 20 章与第一篇第 7 章。

### 22.2.1 硬件事实:三色 LED 在 PA00/PA01/PA02,低电平点亮

本板的三色 LED 接 **PA00(红)/PA01(绿)/PA02(蓝)**,且是 **active-low(低电平点亮)**:

```c
/* gpio_out.h */
#define LED_OUT_PORT  (PortA)
#define LED0_PIN      (Pin00)   // PA00 (红)
#define LED1_PIN      (Pin01)   // PA01 (绿)
#define LED2_PIN      (Pin02)   // PA02 (蓝)
#define LED_OUT_PIN_NUM (3u)
```

`gpio_out_init()` 把这三根脚配成推挽输出,并先全部 `PORT_SetBits` 拉高 → **初始全灭**(active-low:高=灭,低=亮):

```c
/* gpio_out.c (节选) */
stc_port_init_t stcPortInit;
MEM_ZERO_STRUCT(stcPortInit);
stcPortInit.enPinMode = Pin_Mode_Out;
PORT_Init(LED_OUT_PORT, LED0_PIN, &stcPortInit);
PORT_Init(LED_OUT_PORT, LED1_PIN, &stcPortInit);
PORT_Init(LED_OUT_PORT, LED2_PIN, &stcPortInit);
/* 初始全灭: SetBits=OFF(高电平) */
PORT_SetBits(LED_OUT_PORT, LED0_PIN);
PORT_SetBits(LED_OUT_PORT, LED1_PIN);
PORT_SetBits(LED_OUT_PORT, LED2_PIN);
```

> 注意 active-low 的"反直觉":`LED_R_ON()` = `PORT_ResetBits`(拉低→亮),`LED_R_OFF()` = `PORT_SetBits`(拉高→灭)。写驱动时把"亮/灭"封装成 `led_on/led_off`,业务层就不必再纠结电平极性(第 20 章的例程也是这样封装的)。

### 22.2.2 LED 任务函数

`g_u8LedMode` 是控制 LED 模式的全局量(`led` 命令写、LED 任务读,详见 22.6)。三种模式:

```c
/* bsp_led.h */
#define LED_MODE_BLINK  (0u)   /* 闪烁(心跳, 默认) */
#define LED_MODE_ON     (1u)   /* 常亮 */
#define LED_MODE_OFF    (2u)   /* 常灭 */
```

任务壳只做"循环 + 调用 + 阻塞":

```c
/* bsp_led.c (节选) */
static void led_on(uint8_t i)  { /* PORT_ResetBits(LED_OUT_PORT, LEDx_PIN) */ }
static void led_off(uint8_t i) { /* PORT_SetBits   (LED_OUT_PORT, LEDx_PIN) */ }

static void vLedTask(void *pvParameters)
{
    uint32_t u32Cnt = 0ul;
    uint8_t  u8Idx  = 0u;
    (void)pvParameters;

    for (;;)
    {
        switch (g_u8LedMode)
        {
        case LED_MODE_ON:        /* 常亮: 三灯全亮 */
            led_on(0); led_on(1); led_on(2);
            break;
        case LED_MODE_OFF:       /* 常灭: 三灯全灭 */
            led_off(0); led_off(1); led_off(2);
            break;
        case LED_MODE_BLINK:     /* 默认: 三灯轮流闪, 一次只亮一颗 */
        default:
            led_off(0); led_off(1); led_off(2);
            led_on(u8Idx);
            u8Idx = (u8Idx + 1u) % LED_OUT_PIN_NUM;
            break;
        }

        if ((++u32Cnt % 2u) == 0u)   /* 每 1s: 500ms * 2 拍 */
        {
            g_u32Sec++;
        }

        vTaskDelay(pdMS_TO_TICKS(500));   /* 阻塞 500ms, 让出 CPU */
    }
}
```

两点说明:
1. **`blink` 不是"整颗灯翻转",而是"三色轮流亮"**(红→绿→蓝→红…),每 500ms 切换一颗。这是本工程的"心跳灯"观感,和裸机例程"三灯一起翻转"同源,但实现上由 `u8Idx` 在三个引脚间轮转。
2. **`g_u32Sec` 在 LED 任务里自增**,不是独立任务。它代表系统运行秒数,`uptime` 命令会读它(第 27 章)。

### 22.2.3 创建 LED 任务

`bsp_led_init()` 先初始化 GPIO,再 `xTaskCreate` 建任务(优先级 1,与裸机例程的节拍一致):

```c
void bsp_led_init(void)
{
    gpio_out_init();   /* 配置 PA00/PA01/PA02 为输出 (初始为灭) */
    xTaskCreate(vLedTask, "LED", configMINIMAL_STACK_SIZE, NULL, 1, NULL);
}
```

## 22.3 xTaskCreate:六个参数怎么用、为什么这么填

任务函数写好了不会自己跑,必须**显式创建**,交给调度器:

```c
BaseType_t xTaskCreate(
    TaskFunction_t        pvTaskCode,      /* ① 任务函数指针 */
    const char * const    pcName,          /* ② 任务名(调试用) */
    configSTACK_DEPTH_TYPE usStackDepth,   /* ③ 栈深度,单位是"字" */
    void *                pvParameters,    /* ④ 传给任务的参数 */
    UBaseType_t           uxPriority,      /* ⑤ 优先级 */
    TaskHandle_t *        pxCreatedTask);  /* ⑥ 任务句柄(输出,可 NULL) */
```

本工程的写法(节选自 `bsp_led_init` 与 `Console_Init`):

```c
xTaskCreate(vLedTask,      "LED",          configMINIMAL_STACK_SIZE,       NULL, 1, NULL);
xTaskCreate(prv_shell_task,"ConsoleShell", configMINIMAL_STACK_SIZE + 256, NULL, 2, NULL);
xTaskCreate(prv_print_task,"ConsoleOut",   configMINIMAL_STACK_SIZE + 64,  NULL, tskIDLE_PRIORITY + 1, NULL);
```

### 决策点一:栈深度为什么 ConsoleShell 多给 256 字、ConsoleOut 多给 64 字?

回顾第 17 章的栈估算——**最深调用链 + 最大局部数组 + 余量**:

- `vLedTask` 逻辑极简,用最小栈 `configMINIMAL_STACK_SIZE` 即可。
- `prv_shell_task` 里有行编辑缓冲、历史缓冲、VT100 重绘等较多局部状态,且调用链比 LED 深,所以额外加 **256 字(= 1KB)**。
- `prv_print_task` 有 `console_msg_t` 局部结构,加 64 字余量。

**给少了的后果是栈溢出 → HardFault**,表现为"跑一段时间莫名死机",而且很难定位。宁可先给大一点,跑通后用 `uxTaskGetStackHighWaterMark()` 看实际水位再回收(第 23 章)。

### 决策点二:优先级为什么 ConsoleShell=2,LED=1?

- **ConsoleShell 给高(2)**:串口字符由中断塞进 ring buffer 并经信号量唤醒,交互任务必须及时响应输入,否则"跟手感"变差;它可以抢占 LED 等低优先级任务(第 18 章抢占)。
- **LED 给 1**:慢节奏周期性任务,谁先谁后无所谓,同优先级靠**时间片**轮转(第 18 章),谁都不会被饿死。
- **ConsoleOut 给 `tskIDLE_PRIORITY + 1`**:异步打印优先级比空闲略高,但低于业务任务,保证"产生日志"不会反过来卡住业务,又能在 CPU 空闲时把日志发完。

> 再次提醒:**任务优先级数值越大越高**,和 NVIC 中断优先级方向相反(第 18、19 章)。

### 另外两个参数

- **④ `pvParameters`**:想让多个任务共用同一个函数、但传不同参数时用(比如两个 LED 任务传不同引脚)。本工程不用,填 `NULL`。
- **⑥ 句柄**:后续要 `vTaskDelete` / `vTaskSuspend` / `vTaskPrioritySet` 时才需要保存句柄(第 23 章);用不到就填 `NULL`。

### 返回值一定要看

```c
if (xTaskCreate(vLedTask, "LED", 128, NULL, 1, NULL) != pdPASS) {
    /* 创建失败:通常是 configTOTAL_HEAP_SIZE 不够 */
}
```

返回 `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY` 表示**内核堆不够了**(第 21 章的 `configTOTAL_HEAP_SIZE`)。创建任务时判一下返回值,能省掉大量排查时间。

## 22.4 vTaskDelay 与 pdMS_TO_TICKS

### 为什么用 `pdMS_TO_TICKS(500)` 而不是直接写 500?

因为 tick 频率(`configTICK_RATE_HZ`)是可配置的。直接写死数字,一旦把 tick 从 1000 改成 100,`vTaskDelay(500)` 的含义就从 500ms 变成了 5 秒。**用宏换算,代码才与 tick 频率解耦。**

### `vTaskDelay` 的本质(回顾第 16、18 章)

调用后任务进入**阻塞态**,被挂进延时列表,CPU 立刻去跑别的就绪任务;延时到后回到就绪态等待调度。

| 调用处 | 值 | 含义 |
|--------|-----|------|
| `vLedTask` | `pdMS_TO_TICKS(500)` | 每 500ms 翻一次灯 / 走秒一拍 |
| `ConsoleShell` | 阻塞在 `s_rx_sem`(`portMAX_DELAY`) | 无数据不占 CPU,有数据才醒 |
| `ConsoleOut` | 阻塞在输出队列(`portMAX_DELAY`) | 有日志才发,无日志则睡 |

三者都遵循同一条原则:**等待 = 让出 CPU**。区别只在于"等什么"——LED 是主动周期阻塞(`vTaskDelay`),串口侧则用**信号量/队列阻塞**:没有数据时任务根本不占用 CPU,收到中断唤醒才运行。这比第 25 章讲的"ISR 写 buffer、任务 `vTaskDelay(10)` 轮询"更彻底——轮询那 10ms 虽然短,但毕竟还在跑;阻塞等待则是完全让权。串口交互任务的细节见第 27 章。

## 22.5 集中建任务:MX_FREERTOS_Init

工程把"创建任务"收口到一个函数,`main()` 只调一次:

```c
void MX_FREERTOS_Init(void)
{
    Gui_Start();      /* GUI 启动: 开机页(此时 RTOS 刚起来, 与 RTC 无关) */

    bsp_key_init();   /* KEY 任务 */

    bsp_led_init();   /* LED 心跳任务 (见 bsp_led.c) */

    /* 时间"初始化线程": 优先级 0 (低于 GUI), 内部 vTaskDelay 约 3s 让出 CPU,
       不影响其它线程, 完成后自我删除 */
    xTaskCreate(vTimeInitTask, "TimeInit", configMINIMAL_STACK_SIZE + 128, NULL, 0, NULL);
    /* 注: 控制台(ConsoleShell / ConsoleOut)由 main.c 中的 Console_Init() 创建 */
}
```

这样做的好处(呼应第 17.6.3 的分层):`main()` 保持干净,只负责"初始化硬件 → 建任务 → 启动调度器";`MX_FREERTOS_Init` 收口大部分任务创建,便于一眼看清系统里到底有哪些任务、各自优先级多少。串口控制台因为自带 UART 初始化与命令注册,单独放在 `Console_Init()` 里(第 27 章)。

## 22.6 跨任务的一个约定:全局变量怎么安全地用

本章出现了一个必须讲清楚的问题:`g_u8LedMode`(`led` 命令写、LED 读)和 `g_u32Sec`(LED 写、`uptime` 命令读)都是**全局变量**,而第 19 章刚讲过全局变量有竞态风险。

本工程采用的是最简单的一条纪律:**"一个写、一个读"**。

- `g_u8LedMode`:只有 `led` 命令(在 `console.c` 的命令回调里)写,只有 LED 任务读;
- `g_u32Sec`:只有 LED 任务写,只有 `uptime` 命令读。

只要满足"**单一写者**",就不需要加锁——读方最多读到"更新前"或"更新后"的值,不会读到改到一半的坏值(对于 `uint8_t` / `uint32_t` 这类单字长类型的简单读写,不存在撕裂)。这两个全局量都在 `main.c` 里定义为 `volatile`,避免编译器把"反复读"优化成"读一次缓存"。

**这条纪律的边界**:一旦出现"两个任务都写"或"写操作不是一步完成"(比如要同时改年/月/日三个字段),就必须上保护——用队列或互斥量,那就不是本章的方案了(第 24、25 章)。

## 22.7 跑起来看什么,以及怎么排错

编译下载后,你应该看到:

- 板载三色 LED **红→绿→蓝轮流闪烁**(每 500ms 切一颗,即"心跳");
- 串口助手连上后会出现 `> ` 提示符,发 `led on` → 三灯常亮;`led off` → 常灭;`led blink` → 恢复轮流闪;
- 发 `uptime` → 返回一个**随时间增长**的秒数。

如果没看到,按这个顺序查:

| 现象 | 排查 |
|------|------|
| 灯完全不闪 | `bsp_led_init()` 被调用了吗?`xTaskCreate` 返回值是 `pdPASS` 吗?GPIO 初始化(`gpio_out_init`)成功吗? |
| 串口完全没反应 | `Console_Init()` 调了吗?底层在 `console.c`,注意先初始化 UART 再创建交互任务 |
| 灯闪但命令不响应 | 检查 `led` 命令回调里的参数解析(注意 `led off` 长度是 3 不是 2) |
| 一跑就死 / HardFault | 栈给小了;或在中断里调了非 `FromISR` 的 API(第 19 章) |

## 22.8 小结

- 把裸机的一个 super-loop 拆成多个任务:**LED 任务(闪灯 + 走秒)** 做最典型的多任务示范;串口交互(`ConsoleShell` / `ConsoleOut`)被收敛进 `console` 组件,在**第 27 章**单独展开。
- `xTaskCreate` 六个参数里,**栈深度和优先级是需要你做决策**的两个:栈按"调用链 + 局部数组"估,优先级按"谁不能等"定。
- `pdMS_TO_TICKS()` 让代码与 tick 频率解耦;`vTaskDelay` 的本质是**阻塞让权**;串口侧更进一步用**信号量/队列阻塞**,无数据时彻底不占 CPU。
- 任务壳集中建、业务下沉到独立模块(第 17 章分层原则):LED 硬件在 `gpio_out.c`,任务壳在 `bsp_led.c`。
- 跨任务的简单标志可以采用"**单一写者**"的全局变量约定(`g_u8LedMode` / `g_u32Sec`,定义为 `volatile`);一旦出现多方写入,就要上队列或互斥量。
