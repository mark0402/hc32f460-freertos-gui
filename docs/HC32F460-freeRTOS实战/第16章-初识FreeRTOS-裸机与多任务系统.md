## 16.2 什么是 FreeRTOS

FreeRTOS 是一个**实时操作系统内核**。注意"内核"两个字——它不是一个完整的操作系统(不带文件系统、不带网络协议栈、不带 shell),它只专注做一件事:**管理多个执行流(任务),并在它们之间做调度与同步**。

具体到实现上,它是:

- **一个库**:源码就几个 `.c` 文件(`tasks.c`、`queue.c`、`list.c`、`timers.c` 等),和你自己的代码一起编译进同一个固件,跑在同一个地址空间,不需要 MMU。
- **抢占式的**:高优先级的任务一旦需要 CPU,可以立刻把低优先级任务挤下去。
- **可裁剪的**:用不到什么功能就在配置文件里关掉(本工程就把 stream buffer 关了)。
- **免费且商业友好的**:MIT 许可。

它给你的核心能力可以概括成四类,后面四章原理篇正好一一对应:

| 能力 | 解决的问题 | 对应章 |
|------|-----------|--------|
| 任务与调度 | 多个并发活动怎么分 CPU | 第 17、18 章 |
| 通信与同步 | 任务之间怎么安全传数据 | 第 24、25 章 |
| 中断管理 | 硬件事件怎么通知到任务 | 第 19 章 |
| 时间与内存 | 延时怎么算、任务资源从哪来 | 第 18、29 章 |

## 16.3 裸机系统:前后台与超级循环

先看清"没有操作系统"时程序长什么样。本工程的起点——华大官方裸机点灯例程——就是典型代表(第 20 章会带你看完整源码):

```c
int32_t main(void)
{
    /* 初始化 LED 引脚 */
    PORT_Init(LED0_PORT, LED0_PIN, &stcPortInit);

    while (1)
    {
        LED0_TOGGLE(); LED1_TOGGLE(); LED2_TOGGLE();  /* 三色灯一起翻转 */
        Ddl_Delay1ms(500);
    }
}
```

这种结构叫**前后台系统(超级循环,super-loop)**,只有两条执行流:

- **后台(background)**:`main()` 里的 `while(1)`,顺序执行业务逻辑。
- **前台(foreground)**:中断服务程序(ISR),硬件有事时才插入执行。这个例子里连中断都没用。

### 16.3.1 裸机的根本特征:一切靠忙等

`Ddl_Delay1ms(500)` 是**忙等待**——CPU 在里面空转 500ms 数循环。这 500ms 里,CPU 什么有用的事都没干,而且**别的逻辑也别想执行**,因为整个后台就这一条线。

### 16.3.2 想"同时"干多件事,裸机要付出什么代价

假设你在这个点灯程序上,还想同时:随时收串口命令(`led on`)、驱动 LCD 显示时间、扫描按键。用裸机,你被迫把每一件事都改成**非阻塞的状态机**,然后轮流轮询:

```c
while (1) {
    LED_Refresh();   // 不能用 Ddl_Delay1ms,得自己用时间戳判断到没到时间
    UART_Poll();     // 自己去查接收寄存器
    LCD_Refresh();   // 自己判断需不需要重绘
    KEY_Poll();      // 自己消抖、自己计时
}
```

代价是三重的:

1. **每个模块都得自己管理计时**,不能阻塞,逻辑被切碎。
2. **耦合**:任何一个环节写成了阻塞(`while(flag);`),整个系统立刻停摆。
3. **响应不确定**:按键按下的响应延迟,取决于此刻轮询循环转到哪一步。

一句话概括裸机:**看起来在并发,其实是一个人(单线程)在快速轮询,任何一处阻塞都会拖垮全体。**

## 16.4 多任务系统:任务与调度器

RTOS 换了个思路:既然"多件事要并发",那就**把它们真的写成多个独立的执行流**,每个都像一个小小的 `main()`。

- **任务(Task)**:一个永不返回的 `for(;;)` 函数,对应一个并发活动。闪灯是 `vLedTask`(bsp_led.c),收串口是 `prv_shell_task`(console.c),刷屏是 `vGuiTask`(gui.c)。
- **调度器(Scheduler)**:内核里的管理机制,按**优先级**和**时间片**决定此刻该运行哪个任务,并在切换时保存/恢复现场。

本工程最终长成这样**七个业务任务**(另有内核自动创建的空闲任务与定时器服务任务):

| 任务 | 优先级 | 职责 |
|------|--------|------|
| TimeInit | 0 | 时间服务初始化(读 Flash / 起 RTC),完成后自我删除 |
| LED | 1 | 按模式驱动三色 LED,并每约 1s 累加 `g_u32Sec` |
| GUI | 1 | 刷界面、响应按键 |
| NvStore | 1 | 时间记录的 Flash 落盘(`NvStore_Init` 内创建) |
| KEY | 2 | 轮询按键,产出短按/长按事件 |
| ConsoleShell | 2 | 串口交互:行编辑、回显、组行、调 CLI 解析 |
| ConsoleOut | 空闲+1 | 异步输出:取日志队列,用串口发出 |

> 墙上时钟的走时由**硬件 RTC** 的 1 秒周期中断完成,没有独立的"走时任务"(第 26 章)。

每个任务内部逻辑都极简——"该干啥干啥,该等就等"。**复杂性被调度器吸收了,而不是压在你写的状态机里。**

## 16.5 本质区别:阻塞 vs 忙等

这是理解 RTOS 最关键的一点,务必吃透。

同样是"等 500ms":

| | 裸机 | RTOS |
|---|---|---|
| 写法 | `Ddl_Delay1ms(500)` | `vTaskDelay(pdMS_TO_TICKS(500))` |
| CPU 在干什么 | **空转数循环**,500ms 全部浪费 | 当前任务被挂起,**CPU 立刻去跑别的就绪任务** |
| 别的逻辑 | 全部停摆 | 照常运行 |
| 500ms 后 | 自然往下走 | 任务被唤醒,回到就绪态等待调度 |

`vTaskDelay` 的本质是:**任务主动说"我在等一个事件(时间到),这期间别给我 CPU"**,于是调度器把它从就绪列表摘走,让出 CPU。

**这就是 RTOS 能"并发"、能省 CPU 的根本原因——它把"等待"变成了"让权"。** 裸机里等待=CPU 空转;RTOS 里等待=CPU 去干别的。

> 反过来也成立:**如果你在任务里写 `while(flag);` 这样的忙等,RTOS 就退化成了裸机**,同优先级的其它任务会被活活饿死。这是新手最容易犯的错之一。

## 16.6 为什么本项目需要 RTOS

回到本工程:它要同时做**闪灯 + 串口命令行 + LCD 万年历 + 按键扫描**,而且串口命令还要能实时改屏上的时间。

用裸机写,你会得到一个塞满时间戳判断和状态标志的大 `while(1)`,加一个功能就要全局Review一遍会不会阻塞;用 RTOS,每个功能就是:

```c
for (;;) {
    /* 干自己的事 */
    vTaskDelay(...);   /* 或者等队列、等信号量 */
}
```

四个功能互不干扰,新增第五个功能(比如后面加温湿度采集)就是**再加一个任务**,不用动已有的逻辑。这就是本工程从裸机点灯长成图形化万年历所依赖的架构弹性。

## 16.8 小结

- 裸机是**前后台 + 超级循环**,一切靠忙等,任何一处阻塞拖垮全体,加功能要改状态机。
- RTOS 把并发活动拆成**多个任务**,由调度器按优先级分配 CPU。
- 核心区别在于**阻塞 vs 忙等**:RTOS 里"等待"= 让出 CPU,这是它能并发且省 CPU 的根本。
- 本工程要同时做闪灯、串口、刷屏、按键,裸机维护成本高,RTOS 下每加一个功能就是加一个任务。

**下一章**我们把"任务"这个东西彻底拆开:它到底由什么构成、为什么每个任务要有独立的栈、它有哪几种状态、以及切换发生时 CPU 到底做了什么。
