# 第 29 章 工程全景:图形化万年历

从第 20 章到现在,我们一个功能一个功能地往上叠:点灯 → 移植 RTOS → 多任务 → 队列 → 信号量 → 软件定时器 → 串口命令行 → 加屏。现在它们都已经在 `project/` 里跑起来了。

这一章不做新功能,而是**退一步,把整个工程通读一遍**,看清楚这些零件是怎么拼成一台"支持串口配置的图形化万年历"的。读完你应该能在脑子里画出:电从哪来、任务怎么排、数据怎么流。

| | 内容 |
|---|---|
| **本章功能** | 通读 `project/`:文件全景、启动全流程、四条数据流闭环、任务与优先级总表、设计原则收口 |
| **涉及文件** | `main.c`、`User/RTOSThread.c`、`source/console.c/.h`、`source/bsp_key.c`、`source/bsp_led.c`、`source/guislice/gui.c`、`source/app_time.c`、`source/nv_store.c` 等 |
| **要讲清的** | 从复位到主循环的完整链路;时间/设置/输入/调试四条数据流如何闭环;为什么这样分工 |

## 29.1 文件全景

```
project/
├─ User/
│   └─ RTOSThread.c        ← 所有 FreeRTOS 对象的集中创建入口 MX_FREERTOS_Init()
├─ source/
│   ├─ main.c              ← 时钟配置、Console_Init()、main()
│   ├─ console.c / .h      ← 统一控制台:串口 + 分级日志 + 命令行(CONSOLE_CMD_EXPORT 自动注册)
│   ├─ bsp_key.c           ← 按键任务 + 事件队列
│   ├─ bsp_led.c           ← 三色 LED 心跳任务 + g_u32Sec 累加
│   ├─ guislice/
│   │   └─ gui.c / gui.h   ← GUI 任务(界面逻辑全在这里)
│   ├─ app_time.c / .h     ← "时间服务":RTC 初始化 + 走时 + 对时/设时
│   ├─ nv_store.c / .h     ← 时间的非易失存储(日志式 Flash)
│   ├─ gpio_out.c          ← 三色 LED 引脚(PA00/PA01/PA02)
│   ├─ gpio_input.c        ← 按键(PC13)
│   └─ tftlcd.c / .h       ← LCD 底层驱动(画点/线/中文/图)
└─ tools/                  ← 中文字库 / 图片资源生成脚本
```

可以看到,代码是**按"层"和"功能"切分**的:BSP 层(`usart`/`gpio`/`tftlcd`)只管硬件;服务层(`app_time`/`nv_store`)管业务状态;任务层(`RTOSThread`/`cli`/`bsp_key`/`gui`)把前两者组装成并发行为。没有哪个文件既画点又解析命令又管时钟——这是前面各章"分层"思想的最终落点。

## 29.2 启动全流程

```
复位
  │
  ▼
main()
  ├─ SystemClock_Config()        XTAL 8MHz → MPLL → 200MHz
  │                              (晶振起不来自动回退 HRC 16MHz,不卡死)
  ├─ 释放 JTAG 占用的引脚        (避免与复用功能冲突)
  ├─ gpio_out_init()             (三色 LED 引脚)
  ├─ Console_Init()              (串口硬件 + 命令经 CONSOLE_CMD_EXPORT 自动注册;
  │                               共 6 条导出命令: clear/led/echo/gettime/settime/uptime,
  │                               help 由 FreeRTOS-Plus-CLI 内置;
  │                               并创建 ConsoleShell / ConsoleOut 两个任务)
  ├─ MX_FREERTOS_Init()          ← 创建其余任务(见 29.4)
  └─ vTaskStartScheduler()       ← 调度器接管,main() 到此"退休"
```

调度器一启动,下面七个业务任务并发跑起来(ConsoleShell/ConsoleOut 在 `Console_Init` 里更早创建,其余按 `MX_FREERTOS_Init` 里的顺序):

1. **GUI** 最先创建:立刻画闪屏 → 5 秒倒计时(软件定时器)→ 进主界面,开始事件驱动刷新;
2. **KEY** 轮询 PC13,把"长按/短按"投进事件队列;
3. **LED** 按 `g_u8LedMode` 驱动三色 LED(PA00/PA01/PA02),并每约 1 秒累加 `g_u32Sec`;
4. **ConsoleShell** 阻塞等串口数据:取字符、回显、组行、交 CLI 解析;
5. **ConsoleOut** 阻塞等输出队列,把日志/打印异步发往串口;
6. **NvStore** 阻塞等保存队列,把时间记录异步写 Flash;
7. **TimeInit**(优先级最低)**并发**跑:读 Flash 上次时间 → 配 XTAL32 + 启 RTC → 开 1 秒走时 → **自我删除**。

注意 GUI 是"第一个被创建"的,所以用户上电最先看到画面;而真正的时间(RTC 初始化要等约 3 秒晶振稳定)在后台慢慢来,彼此不阻塞。这正是第 26 章"启动优化"的果实。

## 29.3 四条数据流闭环

工程跑起来后,真正有意思的是**数据怎么在任务之间流动**。抓住这四条,整个系统就通了。

### 29.3.1 时间流(自动走时)

```
        RTC 1s 周期中断
             │  (硬件,零 CPU 负担)
             ▼
        AppTime 时间服务
             │  采样进 s_tm,版本号 s_u32Ver++
             ▼
        GUI 主循环:AppTime_GetVersion() 变了?
             │  是 → AppTime_Get() 取数 → AppTime_Format() → gslc_ElemSetTxtStr()
             ▼
        底部状态栏每秒 +1
```

GUI **不自己数秒**,它只盯着"版本号变没变"。RTC 每秒让版本号 +1,GUI 检测到变化才重绘那一行。这就是"界面只展示、不计算"的最直白体现。

### 29.3.2 设置流(屏上改时间)

```
    GUI 设置页(改 g_tm_edit 副本)
             │  点"保存" → AppTime_Set(...)
             ▼
        时间服务:校验 + 请求 NvStore 落盘
             │  成功 → 版本号++
             ▼
        GUI 检测到版本号变化 → 状态栏刷新为新模式
```

无论时间从哪来,**唯一出口都是 `AppTime_Set()`**。它做校验和持久化,界面完全不碰 Flash、不碰 RTC 寄存器。

### 29.3.3 设置流(串口对时)

```
    ConsoleShell 任务收到 "settime 2026-09-02 16:30:00"
             │  CLI 解析 → prvCmdSetTime()
             ▼
        AppTime_Set(...)        ← 和屏上设置走同一个出口!
             │
             ▼
        版本号++ → GUI 状态栏刷新
```

串口对时和屏上设置**殊途同归**:都汇到 `AppTime_Set`。这就是分层的好处——加一种输入方式,不用改时间服务的任何代码。

### 29.3.4 输入流与调试流

```
   按键 PC13 ──► KEY 任务状态机 ──► 事件队列 ──► GUI 消费(切形状/进设置/移焦点)
   串口字节 ──► ConsoleShell 任务 ──► CLI ──► 回调:
                                  led    → 写 g_u8LedMode(LED 任务读)
                                  uptime → 读 g_u32Sec(LED 任务写)
                                  settime→ AppTime_Set
                                  echo/clear/help → 屏/回显
```

`led` 命令和 `uptime` 命令,演示了**最轻量的任务间通信**:一个被单写单读的全局变量(`g_u8LedMode` / `g_u32Sec`),无需队列、无需锁(详见第 27 章)。按键则是典型的生产者-消费者队列模型(第 28 章)。

## 29.4 任务与优先级总表

| 任务 | 创建处 | 优先级 | 栈 | 职责 | 关键通信 |
|---|---|---|---|---|---|
| **GUI** | `Gui_Start` | 1 | +512 | 闪屏 + 界面刷新 | 收 KEY 队列;读时间服务 |
| **LED** | `bsp_led_init` | 1 | 默认 | 驱动三色 LED + 累加秒 | 全局 `g_u8LedMode`/`g_u32Sec` |
| **KEY** | `bsp_key_init` | 2 | +64 | 按键状态机 | 发 KEY 事件队列 |
| **ConsoleShell** | `Console_Init` | 2 | +256 | 行编辑 + 命令分发 | RX 信号量阻塞等;调 `AppTime_Set` |
| **ConsoleOut** | `Console_Init` | 空闲+1 | +64 | 异步日志/打印发送 | 输出队列阻塞等 |
| **NvStore** | `NvStore_Init` | 1 | +64 | 时间记录写 Flash | 保存队列阻塞等 |
| **TimeInit** | `MX_FREERTOS_Init` | 0 | +128 | 读 Flash + 配 RTC,完事自毁 | 调 `AppTime_*` |

优先级规律:**交互类(KEY/ConsoleShell)最高(2)**,保证用户操作和调试命令永远跟手;**界面/LED/NvStore(1)**居中;**异步打印(ConsoleOut,空闲+1)**更低;**最耗时的后台初始化(TimeInit,0)**最低,而且它内部用 `vTaskDelay` 等晶振,即使忙也不会抢占界面。

## 29.5 贯穿全工程的设计原则

把前面各章的原则放在一起看,会发现它们是**一以贯之**的:

1. **界面只展示、不计算**(第 26/28 章):时间、计时、持久化全在服务层,GUI 只负责"变了才重绘"。
2. **耗时初始化拆成独立线程**(第 26 章):`TimeInit` 与 GUI 并发,RTC 3 秒等待不再冻结任何线程。
3. **有界面就必须规避忙等**(第 26 章):任务里一律 `vTaskDelay` 让出 CPU,绝不用 `Ddl_Delay1ms` 霸占内核。
4. **分层:BSP / 任务 / 应用**(第 27 章):串口命令行三层解耦;GUI 不碰硬件、不碰业务。
5. **队列解耦生产者-消费者**(第 24/25/28 章):按键事件、串口数据都走队列,任务互不直调。
6. **轻量共享用全局变量,结构化事件才上队列**(第 27 章):`led`/`uptime` 用全局变量足矣。
7. **脏标记局部重绘**(第 28/39 章):只画变化的部分,不每帧全刷。

这七条不是孤立的"技巧",而是同一个信条的不同侧面:**把"计算/IO/耗时"和"展示/交互"分开,让每个任务只做一件事,靠 RTOS 把它们并发地织在一起。**

## 29.6 小结

- `main()` 只做"配时钟 → 初始化引脚 → `Console_Init()` → 建任务 → 起调度器"五件事,之后就退休(命令由 `CONSOLE_CMD_EXPORT` 自动注册,无需手工注册表)。
- 七个业务任务并发:**GUI**(展示)、**KEY**(输入)、**LED**(指示)、**ConsoleShell**(串口交互)、**ConsoleOut**(异步输出)、**NvStore**(落盘)、**TimeInit**(后台加载,自毁)。
- 四条数据流(时间 / 屏设置 / 串口设置 / 输入+调试)在 `AppTime_*` 时间服务处汇合,形成闭环。
- 所有功能都服从同一套设计原则——分层、解耦、规避忙等、界面只展示。

**下一章**我们对 FreeRTOS 里"本工程没机会深入、但你必须知道存在"的常用机制做一个速览:内存管理、事件组、任务通知、CPU 利用率,给整本书收个尾。
