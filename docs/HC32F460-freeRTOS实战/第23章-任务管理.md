# 第 23 章 任务管理

第 22 章我们创建了任务。这一章管它们:**删掉、暂停、改优先级,以及观测栈和堆用得怎么样**。

| | 内容 |
|---|---|
| **本章功能** | 任务的生命周期管理 + 资源观测 |
| **用到的 API** | `vTaskDelete`、`vTaskSuspend` / `vTaskResume`、`vTaskPrioritySet` / `uxTaskPriorityGet`、`uxTaskGetStackHighWaterMark`、`xPortGetFreeHeapSize` |
| **要讲清的** | 每个 API 什么时候该用、用了以后内存/调度发生了什么 |

## 23.1 删除任务:vTaskDelete

```c
void vTaskDelete(TaskHandle_t xTaskToDelete);
```

两种用法:

```c
vTaskDelete(NULL);        /* 删除自己 */
vTaskDelete(xHandle);     /* 删除别的任务(需要创建时保存句柄) */
```

### 为什么"删除"这件事要单独讲

回顾第 17 章:创建任务时,内核从**堆**里分配了栈和 TCB。删除任务就要把它们还回去。但有个关键细节:

**真正释放内存的动作,不是发生在 `vTaskDelete` 调用的那一刻,而是在空闲任务里完成的。**

原因很直接:一个任务不能在"还运行着"的时候,把自己的栈给拆了(它就站在自己的栈上)。所以 `vTaskDelete` 只是把任务从各种列表里摘掉、标记为待删除,**实际的内存回收由空闲任务(优先级 0)稍后执行**——这正是第 18 章提到"空闲任务负责回收被删除任务的内存"的含义。

**由此得到一条重要的实践结论**:如果你大量动态创建/删除任务,必须保证**空闲任务有机会运行**。要是被一堆高优先级任务占满 CPU、空闲任务一直得不到调度,被删除任务的内存就迟迟回收不了,最终堆被耗尽。

### 什么时候用

- 一次性任务(比如"开机自检""完成一次升级"跑完就可以删);
- 运行中要动态重组功能。

本工程几乎不需要删除任务——只有 `TimeInit` 完成初始化后 `vTaskDelete(NULL)` 自我删除,其余六个业务任务都是启动时创建、终身存在。这也是为什么第 21 章说 heap_1 其实也够用。

> 注意:删除任务时,它自己申请的资源(打开的文件、持有的互斥量、malloc 的内存)**内核不会帮你释放**,必须在删除前自己清理干净。

## 23.2 挂起与恢复:vTaskSuspend / vTaskResume

```c
void      vTaskSuspend(TaskHandle_t xTaskToSuspend);
void      vTaskResume (TaskHandle_t xTaskToResume);
```

### 挂起和阻塞有什么不同

这是最容易混淆的一对概念,回顾第 17 章的四态:

| | 阻塞(Blocked) | 挂起(Suspended) |
|---|---|---|
| 谁触发的 | **任务自己**(我在等一个事件) | **外部**强制(你先别跑) |
| 怎么恢复 | **自动**——等的事发生了内核就唤醒它 | **手动**——必须有人调 `vTaskResume` |
| 典型场景 | 等延时、等队列、等信号量 | 暂时停掉某个功能,何时恢复由别的逻辑决定 |

一句话:**阻塞是"我在等事",挂起是"你给我停下"**。

### 什么时候用

比如设备进入"设置模式"时,暂时挂起数据采集任务;退出设置模式再恢复。比用一堆 `if (g_bPaused)` 标志位去卡住任务要干净得多。

> 注意:在中断里不能调 `vTaskResume`(它不是 `FromISR` 版本),要用 `xTaskResumeFromISR`。

## 23.3 动态改优先级:vTaskPrioritySet / uxTaskPriorityGet

```c
void       vTaskPrioritySet(TaskHandle_t xTask, UBaseType_t uxNewPriority);
UBaseType_t uxTaskPriorityGet(TaskHandle_t xTask);
```

用途:运行时调整任务的"重要程度"。比如设备平时让日志任务优先级很低,进入"调试模式"后临时提高它,让它把日志吐完。

**要注意**:

- 改动会立刻影响调度——如果把某任务提到最高,它会抢占其它任务;
- 优先级数值不能超过 `configMAX_PRIORITIES - 1`(本工程最大 6,见第 21 章);
- 本工程没有动态调整优先级的需求,优先级在创建时定好就固定了。

## 23.4 观测:栈到底用了多少

第 22 章我们"先给大一点,跑通再回收"。这里就是**回收的依据**。

```c
UBaseType_t uxTaskGetStackHighWaterMark(TaskHandle_t xTask);
```

返回的是**栈的历史最小剩余量**(即"高水位线"),单位是**字**。

```c
/* 在需要观测的地方调用(比如通过串口命令触发) */
printf("LED stack left: %lu words\r\n",
       (unsigned long)uxTaskGetStackHighWaterMark(xLedTaskHandle));
```

**怎么用这个数**:

- 返回值越小,说明栈曾经被压得越深,越接近溢出;
- 一般留出 **20%~30% 余量**即可。比如实测剩余 40 字,现在给了 128 字,那可以调到 64 字左右;
- 如果返回值接近 0,**说明已经踩到边上了**,必须加大。

**注意**:这个函数需要创建任务时保存了句柄(第 22 章参数⑥)。如果填 `NULL`,查的是**当前任务**自己。

## 23.5 观测:堆还剩多少

任务栈、TCB、队列都从 `configTOTAL_HEAP_SIZE`(本工程 30KB)这块堆里分配。还剩多少:

```c
size_t xPortGetFreeHeapSize(void);
```

典型用法:在系统跑起来、所有任务和队列都创建完之后,打印一次剩余堆,确认余量充足:

```c
printf("Free heap: %lu bytes\r\n", (unsigned long)xPortGetFreeHeapSize());
```

**如果这个值很小甚至为 0**,就说明"内核对象快把堆吃光了",再创建任务/队列会失败——要么加大 `configTOTAL_HEAP_SIZE`,要么回收那些给过大的任务栈。

> 这也是为什么第 22 章强调"**一定要判断 `xTaskCreate` 的返回值**":堆不够时它会返回 `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY`,而不是悄悄失败。

## 23.6 更进一步:任务列表与运行统计(了解)

FreeRTOS 还提供了两个很方便的调试函数(本工程未启用,需要额外开配置宏):

| 函数 | 作用 | 需要的配置 |
|------|------|-----------|
| `vTaskList()` | 以表格形式列出所有任务的**名字、状态、优先级、栈水位、编号** | `configUSE_TRACE_FACILITY=1`、`configUSE_STATS_FORMATTING_FUNCTIONS=1` |
| `vTaskGetRunTimeStats()` | 列出每个任务**占用 CPU 的百分比** | 上述两个 + 提供一个高精度时基(`configGENERATE_RUN_TIME_STATS=1`) |

调试"某个任务是不是把 CPU 吃满了""哪个任务栈快爆了"这类问题时,这两个函数非常省事。需要在工程里临时打开相关宏,用完再关掉(它们会增加代码体积)。

## 23.7 小结

| API | 作用 | 关键原理 |
|-----|------|---------|
| `vTaskDelete` | 删除任务 | **内存由空闲任务回收**,所以空闲任务必须能跑到;自持资源要自己清理 |
| `vTaskSuspend` / `vTaskResume` | 暂停 / 恢复 | **挂起≠阻塞**:阻塞是等事件自动醒,挂起是外部强制、手动恢复 |
| `vTaskPrioritySet` / `Get` | 改 / 查优先级 | 立即影响调度,上限 `configMAX_PRIORITIES-1` |
| `uxTaskGetStackHighWaterMark` | 查栈历史最小剩余 | 单位是**字**;用于"先给大再回收" |
| `xPortGetFreeHeapSize` | 查堆剩余 | 判断内核对象是否快把堆吃光 |
