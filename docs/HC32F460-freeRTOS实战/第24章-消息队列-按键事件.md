# 第 24 章 消息队列:按键事件

第 22 章我们用"单一写者的全局变量"解决了 LED 模式这种简单标志的跨任务传递。但那种做法有明确边界——这一章讲**当它不够用时该怎么办**。

| | 内容 |
|---|---|
| **本章功能** | 按键的短按/长按事件,从采集任务传给界面任务 |
| **用到的 API** | `xQueueCreate`、`xQueueSend`、`xQueueReceive` |
| **要讲清的** | 为什么这里必须用队列而不能用全局变量;队列的原理;超时参数为什么填 0 |

---

## 24.1 为什么全局变量不够用了

回顾第 22.6 节的约定:全局变量能用,前提是**"一个写、一个读"**。

现在看按键。假设我们用一个全局变量 `g_u8KeyEvent` 存事件:

```c
/* KEY 任务写完 */
g_u8KeyEvent = KEY_EVT_SHORT;

/* GUI 任务读 */
if (g_u8KeyEvent != 0) { 处理; g_u8KeyEvent = 0; }
```

**问题在于丢了事件**:GUI 任务每 20ms 才刷一次屏,如果这期间用户连按了三下,KEY 任务会连写三次 `KEY_EVT_SHORT`,而 GUI 只读到**最后一次**——前两次按键**凭空消失**了。

这就是"**事件流**"和"**状态标志**"的区别:

| | 状态标志(如 `g_u8LedMode`) | 事件流(如按键) |
|---|---|---|
| 语义 | "当前是什么状态" | "发生过什么事" |
| 覆盖 | 新值**覆盖**旧值,没问题 | 新事件**不能**覆盖旧事件,会丢 |
| 需要 | 一个变量就够 | 需要一个**缓冲队列** |

**结论:凡是"发生过几次"这种不能丢的东西,就要用队列。**

---

## 24.2 队列的原理

队列(Queue)是 FreeRTOS 里**最常用**的通信原语,理解四点:

### ① 先进先出(FIFO)的缓冲区

创建时指定"能放几个元素"和"每个元素多大字节"。写入排队,读出按写入顺序。

### ② 传的是**值**,不是引用

`xQueueSend` 会把你要发的数据**完整拷贝**进队列内部的存储区。这意味着:

- 你可以安全地发一个**局部变量**甚至一个结构体——数据已经拷进队列了,原变量销毁也无所谓;
- 反过来,**不要发指向临时数据的指针**——拷进去的只是指针本身,指针指向的东西可能已经失效(见 24.5)。

### ③ 自带线程安全,不需要你加锁

回顾第 19 章的竞态问题:队列内部的读写操作由内核用临界区保护,**多个任务同时读写是安全的**,你不用自己关中断或上互斥量。这正是用它替代裸全局变量的核心价值。

### ④ 可以阻塞等待

`xQueueReceive` 在队列为空时可以**阻塞等待**,直到有数据到来或超时。这让"消费者"任务可以真正睡着等事,而不是轮询——**这是比第 22 章 `vTaskDelay(10)` 轮询更优雅的方式**(见 24.6 的讨论)。

## 24.3 用到的 API

```c
/* 创建:队列长度 + 每个元素字节数,返回句柄(失败返回 NULL) */
QueueHandle_t xQueueCreate(UBaseType_t uxQueueLength, UBaseType_t uxItemSize);

/* 发送:拷贝数据进队尾;xTicksToWait 是队满时的阻塞超时 */
BaseType_t xQueueSend(QueueHandle_t xQueue, const void *pvItemToQueue, TickType_t xTicksToWait);

/* 接收:从队首取出并删除;xTicksToWait 是队空时的阻塞超时 */
BaseType_t xQueueReceive(QueueHandle_t xQueue, void *pvBuffer, TickType_t xTicksToWait);
```

**超时参数 `xTicksToWait` 的三种取值**:

| 取值 | 行为 |
|------|------|
| `0` | **不阻塞**,能干就干,干不了立刻返回 `errQUEUE_FULL` / 失败 |
| `portMAX_DELAY` | **一直等**到成功(把任务挂起,不占 CPU) |
| 具体 tick 数 | 等这么多 tick,超时返回失败 |

## 24.4 本工程实战:KEY 事件队列

代码位于 `project/source/bsp_key.c`。

### 24.4.1 创建队列与任务

```c
#define KEY_QUEUE_LEN   (8u)                 /* 能缓冲 8 个事件 */
static QueueHandle_t s_xKeyQ = NULL;

void bsp_key_init(void)
{
    if (s_xKeyQ == NULL)
    {
        s_xKeyQ = xQueueCreate(KEY_QUEUE_LEN, (UBaseType_t)sizeof(uint32_t));
    }
    xTaskCreate(vKeyTask, "KEY", configMINIMAL_STACK_SIZE + 64, NULL, 2, NULL);
}
```

- 元素类型选 `uint32_t`,用来放事件枚举(`KEY_EVT_SHORT` / `KEY_EVT_LONG`)。
- **队列长度 8** 的意义:用户快速连按几下时,事件先堆在队列里,消费者慢慢取,**不会因为处理不及时而丢事件**。
- KEY 任务优先级 2(和 ConsoleShell 同级),保证按键检测及时;栈比最小栈多 64 字。
- `bsp_key_init()` 由 `main()` 在 `vTaskStartScheduler()` 之前调用一次。

### 24.4.2 生产者:KEY 任务发事件

`vKeyTask` 每 10ms 轮询一次 PC13,用一个小状态机做**去抖**和**长短按判定**:

```c
#define KEY_LONG_PRESS_MS   (1000u)   /* 按住超过 1s 判为长按 */
#define KEY_DEBOUNCE_MS     (30u)     /* 去抖 30ms */
#define KEY_POLL_MS         (10u)     /* 轮询周期 10ms */

static void vKeyTask(void *pv)
{
    key_state_t state = KEY_ST_IDLE;
    uint32_t    debounce_cnt = 0u;
    TickType_t  press_tick = 0u;
    uint8_t     long_fired = 0u;

    (void)pv;
    gpio_input_init();                       /* 配置 PC13 为上拉输入 */

    for (;;)
    {
        uint8_t pressed = (uint8_t)(KEY_IS_PRESSED() ? 1u : 0u);

        switch (state)
        {
        case KEY_ST_IDLE:
            if (pressed != 0u)
            {
                /* 连续多个轮询周期都为低电平才确认按下,滤除抖动 */
                debounce_cnt++;
                if (debounce_cnt >= (KEY_DEBOUNCE_MS / KEY_POLL_MS))
                {
                    state = KEY_ST_PRESSING;
                    press_tick = xTaskGetTickCount();
                    long_fired = 0u;
                    debounce_cnt = 0u;
                }
            }
            else
            {
                debounce_cnt = 0u;
            }
            break;

        case KEY_ST_PRESSING:
            if (pressed != 0u)
            {
                /* 持续按住到达阈值且尚未触发 -> 长按(只触发一次) */
                if ((long_fired == 0u) &&
                    ((xTaskGetTickCount() - press_tick) >= pdMS_TO_TICKS(KEY_LONG_PRESS_MS)))
                {
                    long_fired = 1u;
                    if (s_xKeyQ != NULL)
                    {
                        uint32_t ev = KEY_EVT_LONG;
                        xQueueSend(s_xKeyQ, &ev, 0);      /* ← 超时填 0 */
                    }
                }
            }
            else
            {
                /* 已释放:期间未触发过长按,判为短按 */
                if (long_fired == 0u)
                {
                    if (s_xKeyQ != NULL)
                    {
                        uint32_t ev = KEY_EVT_SHORT;
                        xQueueSend(s_xKeyQ, &ev, 0);      /* ← 超时填 0 */
                    }
                }
                state = KEY_ST_IDLE;
                debounce_cnt = 0u;
            }
            break;

        default:
            state = KEY_ST_IDLE;
            debounce_cnt = 0u;
            break;
        }

        vTaskDelay(pdMS_TO_TICKS(KEY_POLL_MS));           /* 10ms 轮询一次 */
    }
}
```

**为什么 `xQueueSend` 的超时填 0(不阻塞)?** 因为 KEY 任务还要**继续以 10ms 周期轮询引脚**。如果队列满了它就在那儿傻等,按键状态机就停摆了,后续按键全部漏掉。对于"生产者",宁可丢一个事件,也不能让自己卡住。

> 这是很典型的设计取舍:**生产者的节奏不能由消费者决定**。

### 24.4.3 消费者:GUI 任务收事件

`bsp_key.c` 提供了一个封装,本质就是 `xQueueReceive`:

```c
BaseType_t bsp_key_recv(uint32_t *pev, uint32_t xTicksToWait)
{
    if ((s_xKeyQ == NULL) || (pev == NULL))
    {
        return pdFALSE;
    }
    return xQueueReceive(s_xKeyQ, pev, (TickType_t)xTicksToWait);
}
```

GUI 任务这样用(第 28 章会展开):

```c
uint32_t ev = 0;
if (bsp_key_recv(&ev, 0) == pdTRUE)   /* 超时填 0:非阻塞取 */
{
    /* 处理 ev:短按切图形、长按进设置页 ... */
}
```

**为什么 GUI 侧也填 0?** 因为 GUI 任务是个**循环体**:它每 20ms 要刷一次界面,不能卡在"等按键"上。所以它用**非阻塞取**——"有事件就处理,没有就去干刷屏的事"。

### 24.4.4 三种"等待方式"的对比

到这里你已经见过三种让任务"等事"的写法,把它们放一起看:

| 写法 | 适用 | 代价 |
|------|------|------|
| `vTaskDelay(10)` 轮询 | 简单的周期性检查(本工程 KEY 任务,10ms 轮询按键) | 有最多 10ms 延迟,CPU 有唤醒开销 |
| `xQueueReceive(..., 0)` 非阻塞取 | 任务还有别的事要做(本工程 GUI 任务) | 无延迟但需自己循环调用 |
| `xQueueReceive(..., portMAX_DELAY)` 阻塞等 | 任务**只**为这件事而存在 | 响应最快、零空转,但该任务干不了别的 |

本工程 GUI 任务属于第二种(还要刷屏),所以填 0;如果哪天你写一个"专职处理按键"的任务,就该用 `portMAX_DELAY`,让它在没事件时完全睡着,一点 CPU 都不占。

## 24.5 队列传值 vs 传指针

因为队列是**拷贝语义**,所以:

**安全的做法(推荐)**:

```c
typedef struct { uint8_t type; uint32_t value; } evt_t;

evt_t evt = { .type = 1, .value = 123 };
xQueueSend(q, &evt, 0);        /* 把整个结构体拷进队列,局部变量销毁也无所谓 */
```

**危险的做法**:

```c
char buf[32];
snprintf(buf, sizeof(buf), "hello");
xQueueSend(q, &buf, 0);        /* 错!拷进去的是指针(8字节),buf 的内容没被拷 */
```

第二种拷进去的只是**指针值**,而 `buf` 是栈上的局部数组,函数一返回就失效了,消费者拿到的是一个**野指针**。

**如果确实要传大数据**(比如一帧图像),正确做法是:

- 队列里传指针,但**保证指针指向的内存在消费前一直有效**(静态缓冲区、或内存池);
- 或者用**流缓冲区 / 消息缓冲区**(`xStreamBufferCreate` / `xMessageBufferCreate`)——这两个是专为字节流/变长消息设计的,不过本工程 `configUSE_STREAM_BUFFERS=0` 未启用(第 21 章)。

## 24.6 中断里发队列

如果按键改成**外部中断**触发(而不是 10ms 轮询),那么 ISR 里必须用 `FromISR` 版本——回顾第 19 章的铁律:

```c
void KEY_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    uint32_t   ev = KEY_EVT_SHORT;

    xQueueSendFromISR(s_xKeyQ, &ev, &xHigherPriorityTaskWoken);
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);   /* 必要时请求切换 */
}
```

三个要点(第 19 章讲过原因):

1. 必须用 `FromISR` 版本——它**不会阻塞**;
2. 用 `pxHigherPriorityTaskWoken` 输出"是否唤醒了更高优先级任务";
3. 退出前调 `portYIELD_FROM_ISR`,真正的切换由 PendSV 推迟完成。

**本工程为什么用轮询而不是中断?** 因为按键是"人类速度"的事件(最快几十毫秒),10ms 轮询完全够用,而且轮询方案让**去抖和长短按判定**这类逻辑可以写成普通的状态机代码,更简单、更省一个中断资源。这也是第 19 章"延迟中断处理"思想的体现。

## 24.7 跑起来看什么,以及怎么排错

**验证**:短按按键 → 界面切换图形;长按超过 1 秒 → 进入设置页;快速连按几下 → 每一次都被响应(不会丢)。

| 现象 | 排查 |
|------|------|
| 按键完全没反应 | `bsp_key_init()` 被调用了吗?PC13 引脚配置对吗?`s_xKeyQ` 创建成功吗(非 NULL)? |
| 能响应但连按会丢 | 队列长度是否太小?或消费者处理太慢 |
| 长按判定不准 | 检查 `KEY_LONG_PRESS_MS` 与轮询周期的关系;`long_fired` 标志是否漏置 |
| 系统卡死 | 是否在不该阻塞的地方填了 `portMAX_DELAY`?是否在中断里调了非 `FromISR` 的 API? |

## 24.8 小结

- **事件流**(会连发、不能丢)用队列;**状态标志**(新值覆盖旧值)才用全局变量。
- 队列是 **FIFO + 拷贝语义 + 自带线程安全 + 可阻塞** 的通信原语。
- 超时参数三种取值:`0` 不阻塞 / `portMAX_DELAY` 一直等 / 具体 tick 数。
- **生产者不能被消费者拖住**——本工程 KEY 任务发事件填 0,保证 10ms 轮询节奏不停。
- 消费者按"是否还有别的事要做"选非阻塞取(本工程 GUI)还是阻塞等。
- 队列拷的是**值**,发指针时要确保所指内存生命周期足够长。
- ISR 里发队列必须用 `xQueueSendFromISR` + `portYIELD_FROM_ISR`。

**下一章**讲另外两个同步原语——**信号量**(事件通知)与**互斥量**(资源保护),以及它们和队列的分工,再把中断管理在应用层面落实。
