# 第 30 章 其它常用机制速览

前面 9 章应用篇,每一个功能都只用了**刚好够用**的 RTOS 机制:任务、队列、信号量、软件定时器。FreeRTOS 其实还有一整套"周边机制"——内存管理方案、事件组、任务通知、运行时统计等。本工程用不到它们全部(有些甚至刻意砍掉),但作为收尾,你应该**知道它们存在、知道各自解决什么问题、知道本工程为什么没用**。

| | 内容 |
|---|---|
| **本章功能** | 速览四类常用机制:内存管理(heap)、事件组、任务通知、CPU 利用率统计 |
| **涉及 API** | `vPortMalloc`/`vPortFree`、`xEventGroupCreate`/`SetBits`/`WaitBits`、`xTaskNotify`/`ulTaskNotifyTake`、`vTaskGetRunTimeStats`/`uxTaskGetSystemState` |
| **要讲清的** | 每种机制解决什么;本工程用没用、为什么;何时该引入它们 |

## 30.1 内存管理:heap 方案

FreeRTOS 的任务栈、队列、信号量等内核对象,都是在**运行时从一块"堆(heap)"里分配**的(对应 `vPortMalloc` / `vPortFree`,而非 C 库的 `malloc`/`free`)。FreeRTOS 提供了 **5 种 heap 实现**,在移植时(第 21 章)通过 `FreeRTOSConfig.h` 选定一种:

| 方案 | 特点 | 适用 |
|---|---|---|
| heap_1 | 只分配不释放 | 永不删除任务的极简系统 |
| heap_2 | 分配+释放,但不合并碎片 | 老项目兼容 |
| **heap_4** | 分配+释放+**合并相邻空闲块** | 最常用,支持反复建/删任务 |
| heap_3 | 包一层标准 `malloc`/`free` + 临界段 | 想要标准库语义 |
| heap_5 | 同 heap_4,但支持**不连续的多块内存** | 有片外 RAM 等 |

本工程移植时把 **`heap_4.c`** 加进了工程(`FreeRTOSConfig.h` 本身没有 heap 选择宏——用哪种方案由"把哪个 `heap_x.c` 编进工程"决定,见第 21 章),所有 `xTaskCreate` 动态分配的任务栈、以及 `xQueueCreate` 创建的队列,都从这块 heap 里来。**静态 vs 动态**:本工程的任务栈走的是 `xTaskCreate` 的**动态分配**(需要 heap);若用 `xTaskCreateStatic` 则栈由你自己在编译期预留,不依赖 heap。

> 调试提示:栈溢出是 RTOS 项目最常见的隐性 bug。第 23 章讲过用 `uxTaskGetStackHighWaterMark()` 观测"栈的历史最低余量"——余量一直很大说明栈给多了(浪费),余量接近 0 说明快溢出了(要加)。本工程 GUI 任务特意多给了 512 字,就是因为 GUIslice 内部缓冲吃栈。

## 30.2 事件组(Event Group)

**解决的问题**:一个任务要"等好几件事都发生"或"等其中任意一件发生"。比如"等 A 完成 **且** B 完成再开工",用队列得建两个、还得凑齐;事件组用**一个 32 位掩码**就能表达 24 个事件位。

```c
EventGroupHandle_t xEg = xEventGroupCreate();
xEventGroupSetBits(xEg, BIT_A);                 // 生产者置位
EventBits_t x = xEventGroupWaitBits(xEg,
      BIT_A | BIT_B, pdTRUE, pdTRUE, portMAX_DELAY); // 消费者等 A 且 B,到位后清位
```

- `pdTRUE, pdTRUE` 表示"**所有**指定位都置位才返回"且"返回前清掉这些位"(即"等 A 且 B")。
- 若最后一个参数改成 `pdFALSE`,就是"等 A **或** B"。

**本工程没用事件组**。原因是我们的同步需求都很"单纯":按键是一个事件流(队列足够)、时间变化是一个版本号(无锁读)、控制标志是单个全局变量(原子读写)。引入事件组反而增加复杂度。但如果你以后做"等传感器 A、网络 B、按键 C 三者齐了再上传"这类需求,事件组就是首选。

## 30.3 任务通知(Task Notification)

**解决的问题**:很多场景里,队列 / 信号量其实是"一对一通知"的过度设计。任务通知是 FreeRTOS 提供的**轻量版**:直接往某个任务"发信",不占用独立内核对象,**更快、更省内存**。

```c
// 发送方
xTaskNotify(xGuiTaskHandle, 0x1, eSetBits);     // 给 GUI 任务置位 0x1
// 接收方(GUI 任务里)
uint32_t ul; xTaskNotifyWait(0, 0xFFFFFFFF, &ul, portMAX_DELAY);
```

任务通知可以模拟:二值信号量、计数信号量、事件组、甚至带数据的"轻量队列"(用 `xTaskNotify` 的 value 传一个 32 位数)。

**本工程没用任务通知**,而是用队列传按键事件。这更多是"风格选择 + 教学考虑"——队列更直观、更能体现第 24 章的"生产者-消费者"模型;而且按键事件是**多类型**(长按/短按)且需要缓冲(用户可能连按),队列的 FIFO + 长度天然合适,任务通知的"单槽"反而要额外处理。知道有这个更轻的量级选项即可。

## 30.4 互斥量与本工程的"免锁"设计

第 25 章讲过互斥量(`xSemaphoreCreateMutex`)是用来保护**共享资源**的。但回头看本工程,你会发现**几乎不需要互斥量**:

- **LCD 只有 GUI 任务碰**——没有第二个任务去画屏,自然不存在竞争;
- **时间数据靠"版本号 + 无锁读"**——`AppTime_Get()` 只是把 `s_tm` 拷给调用者,GUI 读、RTC 中断写,但 GUI 只在"版本号变了"那一刻拷贝一帧快照,谈不上长期持有;
- **控制标志是单写单读的全局变量**(`g_u8LedMode`/`g_u32Sec`)——8 位/32 位的一次性赋值天然原子,无需加锁(第 27 章)。

所以本工程把"共享可变状态"压到了最低:能独占就独占(屏),能快照就快照(时间),能原子就原子(标志)。**只有在"多个任务长期持有同一份会变的资源"时才上互斥量/临界段**——比如以后若让 ConsoleShell 任务和 GUI 任务都去写同一块显示缓冲,那时才需要。这正印证了第 19/25 章的基调:**临界段和锁是"不得已才用"的武器,能靠架构避开就别用。**

## 30.5 CPU 利用率与运行时统计

想知道"CPU 到底忙不忙、哪个任务最吃 CPU"?FreeRTOS 提供两套观测手段:

- **`uxTaskGetSystemState()`**:一次性取所有任务的栈高位、状态、运行时间,适合自己排版打印;
- **`vTaskGetRunTimeStats()`**:直接生成一张"每个任务占了多少 CPU 百分比"的表,前提是开了运行时统计(用一个更高精度的定时器给 FreeRTOS 打点)。

**本工程未开启运行时统计**。日常调试里,判断"卡不卡"更朴素也够用:看任务是不是都在 `vTaskDelay` 让出 CPU(空闲任务能跑到),而不是死循环霸占。一旦某个任务忘了 `vTaskDelay`、或临界段太长,空闲任务占比就会掉、界面就会卡——这时候再决定要不要开 `vTaskGetRunTimeStats` 精确定位。

## 30.6 小结

- **内存管理**:内核对象从 heap 分配,5 种方案在移植时选定;栈溢出用栈水位观测来防。
- **事件组**:用 32 位掩码表达"多事件与/或"等待;本工程需求单纯,用队列/全局变量已够,未引入。
- **任务通知**:轻量级的一对一通知,比队列快省;本工程为教学清晰用队列传按键。
- **互斥量**:本工程靠"独占/快照/原子"三招把共享压到最低,几乎不需要锁——锁是不得已才用的武器。
- **CPU 利用率**:`vTaskGetRunTimeStats` 可精确定位吃 CPU 的任务;本工程未开,靠"任务是否让出 CPU"即可判断卡顿。
