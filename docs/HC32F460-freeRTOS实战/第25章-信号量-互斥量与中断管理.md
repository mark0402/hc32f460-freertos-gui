# 第 25 章 信号量、互斥量与中断管理

第 24 章的队列解决"传数据"。但有些场景**不需要传数据,只需要一个信号**——比如"数据到了,你来处理"。这一章讲这类**同步原语**,并把第 19 章的中断管理落到应用层。

| | 内容 |
|---|---|
| **本章功能** | 事件通知(信号量)与独占资源保护(互斥量);中断与任务的协作方式 |
| **用到的 API** | `xSemaphoreCreateBinary` / `Counting` / `Mutex`、`xSemaphoreTake` / `Give`,以及它们的 `FromISR` 版本 |
| **要讲清的** | 三者各自解决什么不同的问题,以及怎么选 |

---

## 25.1 先分清:队列、信号量、互斥量各解决什么问题

这是最容易乱的地方。记住它们**解决的不是同一件事**:

| 原语 | 解决什么问题 | 传数据吗 | 典型场景 |
|------|-------------|---------|---------|
| **队列(Queue)** | 任务间**传递数据** | **传**,拷贝一份数据 | 按键事件、传感器数据、命令 |
| **信号量(Semaphore)** | **通知"某事发生了"**,或**给资源计数** | 不传,只记"次数" | ISR 通知任务;还剩几个空位 |
| **互斥量(Mutex)** | **保护独占资源**,保证同一时刻只有一个任务能用 | 不传,是一把"锁" | 多个任务都要写 LCD / 操作 SPI 总线 |

一句话:**要传内容用队列,只要"通知一下"用信号量,要"独占"用互斥量。**

---

## 25.2 二值信号量:最轻量的"事件通知"

### 25.2.1 它是什么

二值信号量只有两个状态:**空(0)/ 有(1)**。可以理解成"一个长度为 1、但不存内容的队列"——它只记"有没有被 give 过"。

```c
SemaphoreHandle_t xSemaphoreCreateBinary(void);

BaseType_t xSemaphoreTake(SemaphoreHandle_t xSemaphore, TickType_t xTicksToWait);  /* 取(等) */
BaseType_t xSemaphoreGive(SemaphoreHandle_t xSemaphore);                           /* 给(通知) */
```

- `Take`:如果信号量是"有",取走变"空",立刻返回;如果是"空",**阻塞等待**(超时参数用法同队列)。
- `Give`:置为"有",如果有任务正等着它,那个任务被唤醒。

### 25.2.2 典型用法:让任务"睡着等中断"

这是第 19 章"延迟中断处理"的**标准写法**:

```c
/* 中断来了:只给个信号,不干别的 */
void XXX_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    xSemaphoreGiveFromISR(xSem, &xHigherPriorityTaskWoken);
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

/* 任务:平时睡着,信号一到立刻干活 */
static void vHandlerTask(void *pv)
{
    for (;;) {
        if (xSemaphoreTake(xSem, portMAX_DELAY) == pdTRUE) {   /* 一直等信号 */
            /* 真正的处理逻辑 */
        }
    }
}
```

**好处**:任务在没事件时**完全阻塞,一点 CPU 都不占**;事件一到,立刻被唤醒。比"轮询 + `vTaskDelay`"响应更快、更省电。

### 25.2.3 本工程正在用它:串口接收

本工程的串口接收(第 27 章)正是上面那套:RX 中断把字节塞进 ring buffer 后调 `xSemaphoreGiveFromISR`,交互任务 `prv_shell_task`(ConsoleShell)用 `xSemaphoreTake(s_rx_sem, portMAX_DELAY)` 阻塞等——**有数据立刻醒,没数据完全睡**。

相比早期"ISR 写 buffer、任务 `vTaskDelay(10)` 每 10ms 轮询"的写法,它消除了最多 10ms 的延迟,也没有没数据时的空转唤醒。你改造自己的工程时,可以直接沿用这一形态。

**注意**:二值信号量适合"一对一通知"。如果 ISR 连续来了多次而任务还没处理完,**多次 give 会被合并成一次**(它只有 0/1 两个状态),可能丢事件——这种"不能丢次数"的场景要用**计数信号量**或队列。

---

## 25.3 计数信号量:给资源计数

```c
SemaphoreHandle_t xSemaphoreCreateCounting(UBaseType_t uxMaxCount, UBaseType_t uxInitialCount);
```

它记录一个**计数值**,`Give` 加一,`Take` 减一,减到 0 再 Take 就阻塞。

两种典型用途:

1. **事件计数**:记录"发生了几次"(弥补二值信号量会合并的缺点)。每发生一次 `Give` 一次,任务 `Take` 一次处理一个。
2. **资源计数**:表示"还剩几个可用资源"。比如有 3 个相同的缓冲区,初始计数 3,任务要用就 `Take`(减到 0 时说明用光了,后来的任务阻塞等),用完 `Give` 回去。

## 25.4 互斥量:保护独占资源

### 25.4.1 为什么需要它

假设 LCD 被两个任务同时操作:GUI 任务正在刷一屏图形,刷到一半被日志任务抢占,日志任务也去写 LCD——**屏幕就花了**。

这类"同一时刻只允许一个使用者"的资源,需要一把**锁**:

```c
SemaphoreHandle_t xSemaphoreCreateMutex(void);

/* 用之前拿锁,用完必须放锁 */
xSemaphoreTake(xLcdMutex, portMAX_DELAY);
LCD_DrawSomething();            /* 临界段:独占 LCD */
xSemaphoreGive(xLcdMutex);
```

`Take` 和 `Give` **必须成对出现**,而且临界段要尽量短——否则别的任务会一直堵着。

### 25.4.2 互斥量 ≠ 二值信号量

它们 API 长得像,但**能力不同**:

| | 二值信号量 | 互斥量 |
|---|---|---|
| 谁都能 Give 吗 | **能**(常用于"任务 A 等、ISR 通知") | **不能**,谁 Take 谁 Give(**所有权**) |
| 支持递归 | 不支持 | 支持(递归互斥量) |
| **优先级继承** | 无 | **有** |
| 能在 ISR 里用 | 可以(`GiveFromISR`) | **不可以** |

### 25.4.3 优先级继承:解决"优先级反转"

这是一个真实存在、且很难查的问题。设想:

1. **低优先级任务 L** 拿到了 LCD 互斥量,正在写屏;
2. **高优先级任务 H** 也需要 LCD,于是 `Take` 阻塞,等 L 放锁;
3. 此时**中优先级任务 M** 就绪了——它不需要 LCD,优先级又比 L 高,于是**抢占了 L 开始跑**。

结果:**H 在等 L,而 L 被 M 压着不能跑**,于是 M(中)实际上跑在了 H(高)前面。这就是**优先级反转**——高优先级任务的响应时间取决于一个不相干的中优先级任务。

**互斥量的优先级继承**解决这个问题:当 H 阻塞在 L 持有的锁上时,内核会**临时把 L 的优先级提升到 H 的级别**,让 L 尽快跑完、放锁;放锁后 L 恢复原优先级。这样 M 就没机会插队了。

**二值信号量没有这个能力**,所以**做资源保护必须用互斥量,而不是二值信号量**。

### 25.4.4 本工程的情况

本工程的 LCD **由 GUI 任务独占**,不存在争用,所以没有上互斥量(`configUSE_MUTEXES=1` 已开启,随时可用)。

但你要清楚:**一旦有第二个任务也要写屏(比如日志任务想在屏上打一行),就必须给 LCD 加互斥量**,否则迟早花屏。

## 25.5 中断管理在应用层的落实

把第 19 章的原理落到写代码上,就是下面这套规则。

### 25.5.1 中断里能调什么

| 中断优先级(数值) | 能调用 |
|------------------|--------|
| **< 5**(更高) | **任何 FreeRTOS 函数都不能调**。只做纯硬件操作(清标志、读写自己的缓冲) |
| **≥ 5** | 只能调 `FromISR` 版:`xQueueSendFromISR`、`xSemaphoreGiveFromISR`、`xTaskNotifyFromISR` … |

对应的 API 对照:

| 任务里 | 中断里 |
|--------|--------|
| `xQueueSend` | `xQueueSendFromISR` |
| `xQueueReceive` | `xQueueReceiveFromISR` |
| `xSemaphoreGive` | `xSemaphoreGiveFromISR` |
| `xTaskNotify` | `xTaskNotifyFromISR` |
| `vTaskResume` | `xTaskResumeFromISR` |
| **互斥量的 Take/Give** | **没有 FromISR 版——互斥量不能在 ISR 里用** |

### 25.5.2 本工程的串口 ISR:中断里只干最小的事

本工程串口 RX 中断(`console.c` 的 `prv_rx_irq_cb`)的做法是:**把收到的字节写进 ring buffer,然后 `xSemaphoreGiveFromISR` 唤醒交互任务,最后 `portYIELD_FROM_ISR`**——ISR 自身只有几微秒。

它展示了中断设计的两条纪律:

- ISR 极短,只做"搬数据 + 发通知",解析、回显、组行全部留给任务;
- 中断优先级数值比 `configMAX_SYSCALL_INTERRUPT_PRIORITY`(本工程 5)更**大**,所以允许调用 `FromISR` API(第 19 章那条线)。

| 方案 | 延迟 | 复杂度 | 说明 |
|------|------|--------|------|
| ISR 只写 buffer + 任务轮询 | ≤ 10ms | 最低 | 简单,但有空转唤醒 |
| ISR 写 buffer + `GiveFromISR`(本工程) | **立即** | 稍高 | 任务阻塞等,零空转 |

本工程选了后者:人机交互要"跟手",而阻塞等待的实现并不比轮询复杂。

### 25.5.3 延迟中断处理:本工程的两个实例

回顾一下这个模式在本工程的两种落地形态:

| 场景 | ISR 做什么 | 任务做什么 |
|------|-----------|-----------|
| **串口** | 收一个字节 → 塞 ring buffer + `GiveFromISR` | `prv_shell_task`(ConsoleShell)阻塞取字符、回显、组行、交 CLI 解析 |
| **按键** | *(没有 ISR,直接轮询)* | `vKeyTask` 10ms 轮询、去抖、判长短按 → 发队列 |

两者都遵循同一原则:**把耗时的、可能阻塞的、复杂的逻辑,全部放到任务里去做**。

## 25.6 怎么选:一个决策表

| 你的需求 | 选什么 |
|---------|--------|
| 要传数据,且不能丢(按键、采样值) | **队列** |
| 只是通知"事情发生了",不传内容 | **二值信号量** |
| 要统计"发生了几次" / "还剩几个资源" | **计数信号量** |
| 保护一个独占设备(LCD、SPI、Flash) | **互斥量** |
| 在 ISR 里通知任务 | 信号量 / 队列的 **`FromISR` 版** |
| ISR 里想保护资源 | **不行**——改成延迟到任务里处理 |

---

## 25.7 小结

- **队列传数据、信号量做通知/计数、互斥量做独占保护**,三者分工明确。
- 二值信号量是"长度为 1 但不存内容的队列",适合 ISR 通知任务,让任务**阻塞等待而非轮询**。
- **互斥量有所有权和优先级继承**,做资源保护必须用它,不能用二值信号量代替;且**不能在 ISR 里用**。
- 优先级反转靠**优先级继承**解决,这是互斥量相对信号量的关键优势。
- 中断里:数值 < 5 不碰任何 RTOS API;≥ 5 只用 `FromISR` 版 + `portYIELD_FROM_ISR`。
- 本工程串口用"**ISR 写 buffer + `GiveFromISR`、任务阻塞 Take**"的方案:有数据立刻醒、没数据完全睡,没有轮询的空转与延迟。

**下一章**补一个本工程实际在用的机制:**软件定时器**——用它做开机 5 秒闪屏倒计时,并把"墙上时钟"从界面里抽出来做成独立的"时间服务"(第 26 章)。它既是第 24/25 章的自然落点,也为再下一章的**串口命令行 console**(第 27 章)铺路。
