## 2.1 从"点灯"到"画界面"的思维跃迁

写过一个"上电 → 初始化 → while(1) 里轮询按键、控制外设"的单片机程序吗？那种程序是**线性**的：同一时刻通常只做一件事，状态就藏在那几个全局变量里。

GUI 程序不同，它有两条必须同时成立的"真相"：

- **真相一：屏幕上的内容是"当前状态"的快照**。某一刻，屏上显示着 4 个按钮、一个时钟、一段中文。这个画面，完全由"此刻的程序状态"决定。
- **真相二：状态会随时变**。用户按了一下键，选中项变了；时钟走了一秒，时间变了。状态一变，屏幕上对应的那块区域就得跟着变。

于是 GUI 程序的骨架永远是：

```
不断地：
   1. 看看状态有没有变（或输入有没有来）
   2. 把"变了的那部分"重新画一遍
```

这个"重新画一遍变了的局部"的动作，就叫**重绘（redraw）**。重绘是 GUI 编程的心脏，后面所有机制都围着它转。

【提示】如果你写过"在 1602 液晶上显示温度，每秒刷新一次"的代码，那么你已经写过最简陋的 GUI 了——那个 `lcd_show(temp)` 每秒调用一次，就是一次重绘。复杂 GUI 只是把"重绘什么、怎么重绘"管理得更精细。

## 2.2 画面是怎么"画"出来的：四个层级

任何界面，无论多花哨，都建立在四个逐层叠加的绘制能力上：

```
第 4 层  控件（Control）
        └ 按钮、文本框、进度条……它们是"有行为、有状态"的画图单元
第 3 层  文本（Text）
        └ 把字符/汉字按字体画成点阵
第 2 层  图形（Shape）
        └ 点、线、矩形、圆、多边形
第 1 层  像素（Pixel）
        └ 在 (x,y) 点亮一个指定颜色的点
```

逐层举例：

- **像素**：`LCD_Draw_ColorPoint(10, 20, GREEN)` —— 在 (10,20) 点一个绿点。这是基石，所有上层都靠它。
- **图形**：用一堆像素点连成 `LCD_DrawLine(0,0,100,100)`，或填一块 `LCD_Fill(x0,y0,x1,y1, color)`。
- **文本**：查字模，把"字"翻译成一个个该亮的点，逐点画。英文 8×16，中文 16×16。
- **控件**：一个"按钮"本质上 = 一个圆角矩形 + 里面的文字 + "是否被按下"的状态颜色。它把"图形 + 文本 + 状态"打包成一个可复用的单元，并附带行为（被点了怎么办）。

理解了"控件 = 图形 + 文本 + 状态 + 行为"这个拆解，你就不会被 GUIslice 里那一堆"元素类型"吓到——它们全是这套基础积木的组合。

【动手试】在脑子里拆解你手机上的"设置"界面：标题栏、列表项、开关按钮、滑块……它们分别由哪几层拼成？开关按钮的"开/关"两种样子，本质是不是"同一个图形 + 不同状态 + 不同文本"？

## 2.3 什么是"重绘"，为什么离不开它

回到 2.1 的骨架。假设屏幕上有一个按钮，用户按了一下，按钮要"亮起来表示被选中"。

如果不重绘会怎样？按钮的图形早画在屏上了，屏自己不会变。所以我们**必须主动**把按钮那块区域重画一遍——这次用"选中色"。

重绘有两种风格，理解它们的差异，是理解 GUIslice 的关键：

| 风格 | 思路 | 例子 |
|---|---|---|
| **全量重绘** | 每次状态变化，把整屏清空重画 | 简单，但慢、可能闪 |
| **局部重绘（脏矩形）** | 只重画"变了的那块矩形区域" | 高效，但框架要记录"哪里脏了" |

本工程的取舍：GUIslice 用**局部重绘**（脏矩形），而手绘内容因为没有显存，采用"先刷局部背景、再重画"的等价做法。两者目标一致——**只动该动的地方**。

【注意】"局部重绘"有个隐含前提：框架得知道每个元素画在了哪块矩形里、当前是什么样子。所以 GUI 框架几乎都会让你"创建元素时声明位置和大小"，它不是在跟你客气，是它真的需要这些信息来算重绘区域。

## 2.4 两种 GUI 思路：有帧缓冲 vs 没有帧缓冲

这是理解本工程"怪异写法"的一把钥匙。

### 有帧缓冲（显存）的世界

很多带 LCD 控制器的芯片，有一块和屏幕像素一一对应的内存（Frame Buffer）。在这种情况下：

- 你要"画一个按钮"，其实是**往显存里写颜色数据**；
- 屏幕控制器自动、不停地从显存刷到屏上；
- "重绘"只是改显存里那一小块，屏会在下一个刷新周期自动体现出来；
- 双缓冲还能避免"画到一半被屏扫到"导致的撕裂。

这种世界里，重绘很便宜，也很少出现"残留"问题——因为你能随时"读回"显存看看现在长啥样。

### 没有帧缓冲的世界（本工程）

本工程的屏是**SPI 直驱**，MCU 侧**没有**一块和屏幕对应的显存。这意味着：

- 你"画"一个像素，就是**立刻通过 SPI 把这个像素的颜色推到屏上**；
- 屏上此时是什么，MCU **不知道**，也读不回来；
- 想改一个按钮的选中色？你得**先把它原来的样子擦掉（刷成背景色），再画新的**；
- 如果忘了擦，旧的图形就"残留"在那，和新图形叠在一起变成一团乱麻。

这就是本工程无处不在的**"局部擦写"范式**：

```
先把这一小块刷成背景色 → 再重新画新内容
```

【提示】没有帧缓冲，其实是大多数小屏 MCU 项目的常态（用显存太费 RAM）。所以"先擦后画"的范式，你以后会反复用到，先把它刻进肌肉记忆。

## 2.5 输入：单按键如何驱动完整界面

桌面 GUI 有鼠标键盘，手机有触摸。本工程只有一个接在 PC13 的按键。怎么用"一个键"操作一个多页面界面？

答案是**用"按键语义"模拟复杂操作**。本工程约定：

| 操作 | 触发 | 含义 |
|---|---|---|
| 短按 | 按下后 < 1000ms 释放 | "确认 / 下一项 / 切换选中" |
| 长按 | 按住 ≥ 1000ms | "移动焦点 / 进入下一级" |

于是：

- 主页：短按切换右侧显示的图形，长按进入设置；
- 设置页：长按在字段间移动焦点，短按给当前字段 +1；焦点到"保存"短按提交，"取消"短按丢弃。

这套约定让一个键也能完成"选择—编辑—确认—返回"的完整闭环。其本质是：把"多按键/多手势"压缩成"短按/长按"两个原语，再用状态机解释它们。

【注意】单按键界面的"状态"比多按键更敏感于正确性。一旦焦点状态、页面状态算错，用户就"走不回来"了。所以本工程的页面切换、焦点移动，都走"明确的跳转函数"，而不是散落在各处的 `if`。

## 2.6 本工程选型的取舍

把以上心智模型收口，本工程其实是这样一种权衡：

| 想要 | 约束 | 采取的方案 |
|---|---|---|
| 有控件、能管理多页面 | 不想从零写控件系统 | 用 GUIslice 管按钮框/状态栏 |
| 显示中文 | GUIslice 无中文、本工程约定 C 源码不含中文 | 绕过 GUIslice，自写中文点阵绘制 |
| 画任意图形 | GUIslice 图形能力有限/未启用 | 直接调 `tftlcd` 画线 |
| 不闪、省带宽 | 无帧缓冲 | 局部重绘 + 先擦后画 |
| 单键操作 | 只有 PC13 | 短按/长按状态机 |

所以你看到的工程代码里，GUIslice 和"手绘"是**混在一起**的——这不是混乱，而是一种清醒的取舍：框架管它擅长的，手绘管框架不擅长的。

下一章，我们会把这套心智模型，翻译成 GUIslice 自己的概念语言（元素、页面、重绘、回调）。

## 2.7 本章小结

- GUI 程序骨架 = "检测状态变化 → 重绘变化处"，重绘是心脏。
- 画面四层：像素 → 图形 → 文本 → 控件（控件 = 图形+文本+状态+行为）。
- 有帧缓冲时重绘便宜、可回读；无帧缓冲时必须"先擦后画"，否则残留。
- 单按键靠"短按/长按"两个原语 + 状态机，也能驱动完整界面。
- 本工程让 GUIslice 管它擅长的、手绘管它不擅长的，二者混合。
