## 1.1 我们要做什么

一句话：**在一块很小的 SPI 屏上，做一个能切换的中文人机界面。**

具体落到一个上电后的完整流程：

1. 上电，显示一张 Logo 图片，右上角 5 秒倒计时；
2. 进入主页：左侧 4 个按钮（矩形 / 三角形 / 五角星 / 六芒星），右侧一块区域显示当前选中的图形，底部状态栏显示实时时钟；
3. 长按进入"设置页"：用单键调整年月日时分秒（编辑副本、可保存/取消）；
4. 按设计，还可以继续扩更多页面。

这个需求本身不复杂，但硬件条件相当"抠门"，正因如此，才衍生出后面所有"绕弯子"的设计：

- 屏幕只有 **240×135**，且没有触摸；
- 屏幕是 **SPI 直驱、无帧缓冲**（没有显存可以读回）；
- 编译器是 **ARM Compiler 6（AC6 / armclang）**；中文一律由脚本生成点阵手绘（C 源码不含中文），与编译器是否支持 UTF-8 无关；
- 输入只有一个 **PC13 按键**，靠"短按 / 长按"复用。

理解这些约束，是理解后面每一章的前提。

## 1.2 硬件全景

```
        ┌─────────────┐         SPI3          ┌──────────────┐
        │ HC32F460    │ ─── SCK/MOSI ───────▶ │ ST7789 类屏  │
        │ (200MHz)    │ ─── DC / RST ───────▶ │ 240×135      │
        │ Cortex-M4F  │ ─── PWR ───────────▶ │ RGB565       │
        └─────────────┘                      └──────────────┘
              │
              │ PC13（上拉，按下为低）
              ▼
          一个按键（短按 / 长按）
```

| 硬件 | 规格 / 接法 | 说明 |
|---|---|---|
| 主控 | HC32F460（本工程按 JEUA 例程配置） | 8MHz 晶振 → MPLL(×50÷2) → 200MHz |
| 显示屏 | 240×135 横屏，ST7789 类驱动 | 见 `tftlcd.h` 的 `USE_HORIZONTAL 2` |
| 显示接口 | SPI3：PB06 SCK / PB07 MOSI | 带 DMA 发送，提升刷屏速度 |
| 控制线 | PB08 DC（数据/命令）、PB09 RST、PB03 PWR | 见 `tftlcd.h` 引脚宏 |
| 输入 | PC13，上拉输入 | 单键，按下为低电平 |
| 调试 | USART 串口 | 支持 `settime` 等 CLI 命令 |

【提示】屏的"横屏"是驱动层通过 `USE_HORIZONTAL` 配置出来的。对 GUIslice 来说，它只关心"宽 240、高 135"，至于这个宽高是怎么转出来的，是 `tftlcd.c` 的事。

## 1.3 软件全景

```
┌─────────────────────────────────────────────┐
│ 应用层   gui.c        页面布局 / 状态 / 事件   │  ← 你主要改这里
├─────────────────────────────────────────────┤
│ 框架层   GUIslice      元素 / 页面 / 重绘调度  │  ← 开源库，基本不改
├─────────────────────────────────────────────┤
│ 适配层   gslc_drv_hc32.c  驱动回调映射         │  ← 移植的核心
├─────────────────────────────────────────────┤
│ 驱动层   tftlcd.c        画点/填充/线/字/图   │  ← 现成的底层
├─────────────────────────────────────────────┤
│ 硬件     ST7789 240×135  SPI3 + DMA          │
└─────────────────────────────────────────────┘
        ▲
        │ FreeRTOS 把以上任务调度起来
```

注意两个"层"是本项目特有的：

- **适配层 `gslc_drv_hc32.c`**：GUIslice 是开源框架，它不知道你的屏怎么画点。它定义了一组 `gslc_Drv*` 回调接口，我们要把这组接口**映射到已有的 `tftlcd` 函数**上。这一层就是移植工作量所在。
- **应用层 `gui.c`**：所有页面、所有手绘的中文和图形都在这里。

【提示】"框架层"和"驱动层"之间，正是新手最容易混淆的地方。记住一句话：**GUIslice 决定"画什么、画在哪"，`tftlcd` 决定"怎么把像素送上屏"。**

## 1.4 一个像素是怎么显示出来的

为了建立最底层的直觉，我们追一条最简单的调用链：显示开机 Logo。

1. 应用层调用 `LCD_Show_Image(lx, ly, w, h, g_au8TitansLogo)`;
2. `tftlcd.c` 里的 `LCD_Show_Image` 先设置屏幕的"绘制窗口"（`LCD_Address_Set`），告诉屏"接下来这一块区域要被写入"；
3. 然后把整块图片字节流通过 `LCD_SPI_Send` 交给 SPI+DMA 推送到屏；
4. 屏控制器把字节流按 RGB565 解析成颜色，逐像素点亮。

```868:880:project/source/tftlcd.c
void LCD_Show_Image(uint16_t x, uint16_t y, uint16_t width, uint16_t height, const uint8_t *p)
{
    if(x + width > LCD_Width || y + height > LCD_Height)
    {
        return;
    }

    LCD_Address_Set(x, y, x + width - 1, y + height - 1);

    LCD_DC(1);

    LCD_SPI_Send((uint8_t *)p, width * height * 2);
}
```

【注意】第 3 行的 `if` 是个"静默失败"：图片一旦超出屏幕边界，函数直接 `return`，**既不报错也不画任何东西**。后面你若发现图片不显示，第一反应应该是"是不是越界了"。

这条链说明一件事：**屏幕本质上是"你告诉它写哪、再喂它一串颜色字节"的设备**。GUI 框架的所有"高级"能力，归根结底都是在这条链路上做组织——决定哪些字节、以什么顺序、在什么时机被送出去。

## 1.5 为什么"中文"是个特别麻烦的问题

如果屏幕只显示数字和英文，世界会简单很多——`tftlcd.c` 里已经有一个 8×16 的 ASCII 字库，直接按字符查表画点即可。

但中文不行，有三个层层叠加的障碍：

**障碍一：GUIslice 自带字体只有 ASCII。**

GUIslice 的官方字体是西文字体，没有中文字模。所以中文不能交给 GUIslice 去画。

**障碍二：本工程约定 C 源码不含中文，中文走脚本生成点阵手绘。**

```c
// 本工程不在 .c 里写中文；中文是 Python 脚本生成的十六进制字节数组：
static const uint8_t CNSTR_TITLE[] = {0xE8, 0x83, 0xBD, ...};  // 这是 "能源管理系统"
```

这意味着中文**不能像英文那样以字符串字面量写进 `.c` 文件**——即使编译器（AC6 / armclang）支持 UTF-8，界面中文也由 `gen_chinese_font.py` 取模后手绘，与编译器无关。

**障碍三：屏没有中文点阵，必须自己提供。**

即使编译器支持中文，屏幕控制器也不认识"中文"这种glyph（字形），我们只能把每个汉字预先转成"点阵"（哪些像素亮、哪些不亮），再一个点一个点地画。

这三个障碍合在一起，逼出了本工程的中文方案（第 39 章详述）：

```
Python 用系统中文字体渲染汉字 → 输出十六进制点阵/字节数组 → C 里只有数字，绝不出现中文
```

也就是说，C 源文件里你看到的永远是这种东西：

```c
static const uint8_t CNSTR_SAVE[] = {0xE4, 0xBF, 0x9D, 0xE5, 0xAD, 0x98, 0x00};  // 这是 "保存"
```

【注意】**"改中文 = 改 Python 脚本 → 重跑 → 重编译"**，绝不是去 C 文件里改汉字。这是本工程最重要的一条工作纪律，记牢。

## 1.6 本章小结

- 本系统 = 小 SPI 屏 + 单按键 + 中文界面 + HC32F460 + FreeRTOS + GUIslice。
- 软件分五层：应用(gui.c) → 框架(GUIslice) → 适配(gslc_drv_hc32) → 驱动(tftlcd) → 硬件。
- 屏幕是"先设窗口、再喂颜色字节"的设备；GUI 框架本质是对"喂哪些字节、何时喂"的组织。
- 中文之所以麻烦，是 GUIslice 缺中文、**本工程约定 C 源码不含中文（与编译器无关）**、屏不认中文三件事叠加，必须用"脚本取模"绕开。
