# 第 3 章 配置系统

这一章讲三件事：模块开关怎么工作、配置结构体为什么必须清零、以及 DDL 的错误处理方式。

这些内容不涉及任何具体外设，但它们出现在每一个外设的每一行代码里。理解之后，你会发现所有 DDL 代码都长得差不多，因为它们都在套同一套范式。

---

## 3.1 模块开关机制

### 问题从哪来

第一次从例程复制代码到自己工程时，很多人会遇到这个错误：

```
Error: L6218E: Undefined symbol PORT_Init (referred from main.o)
```

代码一模一样，头文件也包含了，为什么找不到函数？

答案在 `ddl_config.h`。打开文件，你会看到几十行这样的定义：

```c
#define DDL_GPIO_ENABLE        (DDL_OFF)
#define DDL_USART_ENABLE       (DDL_OFF)
#define DDL_SPI_ENABLE         (DDL_OFF)
/* ... */
```

把 `DDL_GPIO_ENABLE` 改成 `DDL_ON`，错误就消失了。

### 它做了什么

回顾上一章的驱动文件结构，头文件里所有内容都被条件编译包着：

```c
/* hc32f460_gpio.h */
#if (DDL_GPIO_ENABLE == DDL_ON)
    /* 枚举、结构体、函数声明 */
#endif
```

源文件也一样：

```c
/* hc32f460_gpio.c */
#if (DDL_GPIO_ENABLE == DDL_ON)
    /* 函数实现 */
#endif
```

所以当开关是 `DDL_OFF` 时：

- 头文件里的声明被预处理器删除 → 编译器认为 `PORT_Init` 这个函数不存在
- 源文件里的实现被删除 → 即使你把 `.c` 加进工程，它也不产生任何代码

两者缺一不可。只有声明没有实现，链接时报 undefined symbol；只有实现没有声明，调用时报隐式声明错误。

### 为什么要这么设计

STM32 标准库没有这层开关，你包含哪个头文件就能用哪个外设。DDL 多这一层，主要的考虑是代码体积。

一个中等复杂度的驱动编译后可能占几 KB 到十几 KB 的 Flash。如果你的项目只用 GPIO 和串口，把 40 个外设的驱动全部编译进去是浪费。开关让你只编译需要的部分。

另外一个作用是让依赖关系显式化。打开 `ddl_config.h`，一眼能看出这个工程用到了哪些外设。这在接手别人的项目时很有价值。

### 该怎么用

**关键原则：把 `ddl_config.h` 当作"产品能力清单"，而不是"例程附属品"。**

原厂的每个例程目录下都有一份 `ddl_config.h`，只打开了那个例程用到的模块。很多人习惯性地"用哪个例程就复制哪个配置"，于是每加一个外设就要重新合并一次配置，很容易漏。

正确的做法是维护**一份**配置，代表你整个产品需要的能力：

```c
/* 我这个工程会用到 GPIO、串口、SPI、DMA、ADC、定时器 */
#define DDL_ICG_ENABLE         (DDL_ON)
#define DDL_UTILITY_ENABLE     (DDL_ON)
#define DDL_CLK_ENABLE         (DDL_ON)
#define DDL_PWC_ENABLE         (DDL_ON)
#define DDL_EFM_ENABLE         (DDL_ON)
#define DDL_SRAM_ENABLE        (DDL_ON)
#define DDL_GPIO_ENABLE        (DDL_ON)
#define DDL_INTERRUPTS_ENABLE  (DDL_ON)
#define DDL_EXTI_ENABLE        (DDL_ON)
#define DDL_USART_ENABLE       (DDL_ON)
#define DDL_SPI_ENABLE         (DDL_ON)
#define DDL_DMAC_ENABLE        (DDL_ON)
#define DDL_ADC_ENABLE         (DDL_ON)
#define DDL_TIMER0_ENABLE      (DDL_ON)
```

以后新增 ADC，只加一行 `DDL_ADC_ENABLE (DDL_ON)`，不用动别的。

### 哪些必须开

有几个开关比较特殊，几乎在所有工程里都应该打开：

`DDL_ICG_ENABLE` 和 `DDL_UTILITY_ENABLE` 在官方模板里默认就是 `DDL_ON`。前者是上电配置，后者提供了 `MEM_ZERO_STRUCT`、`Ddl_Delay1ms`、`DDL_PrintfInit` 这些几乎每份代码都会用到的东西。

`DDL_CLK_ENABLE`、`DDL_PWC_ENABLE`、`DDL_EFM_ENABLE` 三个默认关闭，但实际上只要你不满足于默认的 8MHz 内部时钟、或者要用任何外设，都需要它们。三者的依赖关系是：

**PWC** 提供外设时钟门控 `PWC_FcgXPeriphClockCmd()`。任何外设使用前必须开对应的时钟门，否则寄存器写了也不生效。只要用到一个外设就需要 PWC。

**CLK** 提供时钟树配置。如果你接受复位后的默认 8MHz 内部 RC、从不调用 `CLK_` 函数，理论上可以不开。但只要你想用外部晶振、想升频、想知道当前总线频率，就需要它。

**EFM** 提供 Flash 等待周期设置和 Flash 擦写。时钟升到高频后必须调用 `EFM_SetLatency()` 增加等待周期，否则 CPU 取指出错直接跑飞。想保存参数到内部 Flash 也需要它。

除此之外，`DDL_SRAM_ENABLE` 在升频时也需要，因为 `SRAM_Init()` 配置 SRAM 等待周期。

实际建议：把 ICG、UTILITY、CLK、PWC、EFM、SRAM 这六个一起打开，再按需添加外设。这几项占用的 Flash 很小，却能避免绝大多数"代码看起来对但跑不起来"的问题。

### 另一个必要条件

开关只控制"是否参与编译"。你还要确保对应的 `.c` 文件在 Keil 工程的分组里。很多人开了开关但仍然链接失败，就是因为 `driver/src/hc32f460_xxx.c` 没加进工程。

完整的检查清单：

1. `ddl_config.h` 里对应开关设为 `DDL_ON`
2. `driver/src/hc32f460_xxx.c` 已加入工程分组
3. Include Paths 包含 `driver/inc`
4. 代码里 `#include "hc32_ddl.h"`

## 3.2 hc32_ddl.h 的包含策略

打开任意一个例程的 `main.c`，开头几乎总是：

```c
#include "hc32_ddl.h"
```

只有这一行。这个文件是 DDL 的统一入口，它内部根据 `ddl_config.h` 的开关决定包含哪些驱动头文件：

```c
/* hc32_ddl.h 的简化结构 */
#include "hc32_common.h"
#include "ddl_config.h"

#if (DDL_GPIO_ENABLE == DDL_ON)
    #include "hc32f460_gpio.h"
#endif

#if (DDL_USART_ENABLE == DDL_ON)
    #include "hc32f460_usart.h"
#endif

#if (DDL_SPI_ENABLE == DDL_ON)
    #include "hc32f460_spi.h"
#endif
/* ... 依次类推 */
```

这意味着你**不需要**（也不应该）手动包含 `hc32f460_gpio.h`。只包含 `hc32_ddl.h` 就够了，它会自动把启用的模块都带进来。

如果你的代码里写了 `#include "hc32f460_usart.h"` 却忘了开开关，那个头文件里的内容是空的，问题会更隐蔽。统一用 `hc32_ddl.h` 可以避免这类混乱。

`hc32_ddl.h` 通常会和 `USE_DEVICE_DRIVER_LIB` 这个宏配合使用：

```c
#ifndef USE_DEVICE_DRIVER_LIB
    #error "请在工程预处理器定义里添加 USE_DEVICE_DRIVER_LIB"
#endif
```

如果你的工程报这个错，去 Keil 的 Options → C/C++ → Define 里加上 `USE_DEVICE_DRIVER_LIB`。这是一个编译开关，用来区分"用 DDL 的工程"和"不用 DDL 的工程"。

## 3.3 配置结构体范式

### DDL 的参数传递方式

看看这两个函数的签名：

```c
/* 方式一：参数列表 */
void SomeInit(uint32_t baudrate, uint8_t dataBits, uint8_t stopBits, ...);

/* 方式二：结构体（DDL 采用的） */
en_result_t USART_UART_Init(M4_USART_TypeDef *USARTx,
                            const stc_usart_uart_init_t *pstcInitCfg);
```

DDL 统一采用第二种。所有配置参数打包成一个结构体，传给 Init 函数。

这样做的好处是可扩展——以后要给串口加个新配置项，只要往结构体里加一个字段，不用改所有调用点的函数签名。代价是多了一步：你必须先把结构体填好。

### 为什么必须清零

这是 DDL 编程里最容易出错、后果也最难查的地方。看这段代码：

```c
stc_port_init_t stcPortInit;                  // 定义结构体变量
stcPortInit.enPinMode = Pin_Mode_Out;         // 只设了一个字段
stcPortInit.enPullUp  = Enable;
PORT_Init(PortE, Pin06, &stcPortInit);        // 传进去
```

看起来没问题，但 `stcPortInit` 是**局部变量**，分配在栈上。C 语言不会自动初始化局部变量，所以那几个你没赋值的字段——驱动能力、输出类型、外部中断使能——里面是上次栈使用留下的垃圾值。

结果可能是：LED 亮度异常、引脚行为诡异、或者某个你没注意的功能被意外打开。更糟的是，这类问题往往时有时无，因为栈上的垃圾值取决于之前执行过什么代码。

DDL 提供的解决方式是 `MEM_ZERO_STRUCT` 宏：

```c
#define MEM_ZERO_STRUCT(x)   (memset(&(x), 0, sizeof(x)))
```

用法：

```c
stc_port_init_t stcPortInit;
MEM_ZERO_STRUCT(stcPortInit);          // 先清零，所有字段归零

stcPortInit.enPinMode = Pin_Mode_Out;  // 再设需要的字段
stcPortInit.enPullUp  = Enable;
PORT_Init(PortE, Pin06, &stcPortInit);
```

清零之后，未显式设置的字段都是 0，对应枚举里通常是"默认/禁用"的含义，行为可预测。

**规则：定义配置结构体之后、填充字段之前，立刻 `MEM_ZERO_STRUCT`。** 这个习惯应该形成条件反射。STM32 标准库时代有 `XXX_StructInit()` 做类似的事，HC32 统一用这个宏。

有一种情况可以省略——用初始化列表在定义时就赋值：

```c
const stc_usart_uart_init_t stcInitCfg = {
    UsartIntClkCkNoOutput,
    UsartClkDiv_1,
    UsartDataBits8,
    /* ... */
};
```

这种写法所有字段都显式给出了初值（C 语言规定初始化列表里未列出的成员自动置 0），所以不需要再清零。官方例程里两种写法都能见到。

不过要小心：初始化列表是按**成员声明顺序**对应的，不是按名字。如果驱动升级后结构体成员顺序变了，你的初始化列表就错位了。所以对于会长期维护的代码，用 `MEM_ZERO_STRUCT` + 逐字段赋值更稳妥。

### 配置结构体的命名规律

所有配置结构体都叫 `stc_<外设>_init_t` 或类似形式：

| 外设 | 配置结构体 |
|---|---|
| GPIO | `stc_port_init_t` |
| USART | `stc_usart_uart_init_t` |
| SPI | `stc_spi_init_t` |
| ADC | `stc_adc_init_t` |
| Timer0 | `stc_tim0_base_init_t` |
| DMA | `stc_dma_config_t` |
| 外部中断 | `stc_exint_config_t` |
| 中断注册 | `stc_irq_regi_conf_t` |
| 系统时钟 | `stc_clk_sysclk_cfg_t` |
| MPLL | `stc_clk_mpll_cfg_t` |

在头文件里搜索 `_init_t` 或 `_cfg_t` 就能找到。

## 3.4 返回值与错误处理

### en_result_t

DDL 中大多数初始化和关键操作函数返回 `en_result_t`：

```c
typedef enum en_result
{
    Ok    = 0,   // 成功
    Error = 1,   // 失败
} en_result_t;
```

只有两个值。它不告诉你具体哪里错了，只告诉你成功与否。

官方例程的标准处理方式：

```c
enRet = USART_UART_Init(USART_CH, &stcInitCfg);
if (enRet != Ok)
{
    while (1)      // 失败就死循环，便于调试器定位
    {
        ;
    }
}
```

死循环看起来粗暴，但在嵌入式裸机里是合理的做法——初始化失败意味着硬件配置有问题，继续执行只会产生更难理解的故障。调试时程序卡在这里，你一看调用栈就知道是哪个外设没配好。

在实际项目里，可以根据情况选择更友好的方式：

```c
if (Ok != USART_UART_Init(USART_CH, &stcInitCfg))
{
    printf("USART init failed!\r\n");
    /* 或者：记录错误码、点亮故障灯、进入安全模式 */
}
```

### 什么时候返回值有意义

`en_result_t` 主要出现在两类函数上：

**初始化类**。`XXX_Init()` 通常会检查参数合法性，参数越界时返回 `Error` 而不执行配置。

**需要等待硬件响应的**。`CLK_MpllCmd()` 这类函数可能因为硬件状态不对而失败。

而设置类、读取类的函数多数返回 `void` 或直接返回值本身：

```c
void PORT_SetBits(en_port_t enPort, en_pin_t enPin);        // 无返回
uint16_t USART_RecData(M4_USART_TypeDef *USARTx);           // 返回数据
en_flag_status_t USART_GetStatus(M4_USART_TypeDef*, ...);   // 返回标志
```

对返回 `void` 的函数，出错的可能性很低，检查也没意义。

### 内部参数检查

DDL 的驱动文件开头通常有一组参数检查宏：

```c
#define IS_VALID_PORT(x)  (((x) == PortA) || ((x) == PortB) || ...)
#define IS_VALID_PIN(x)   (((x) == Pin00) || ((x) == Pin01) || ...)
```

这些宏用在函数开头：

```c
en_result_t PORT_Init(en_port_t enPort, en_pin_t enPin,
                      const stc_port_init_t *pstcPortInit)
{
    /* 参数检查 */
    if ((!IS_VALID_PORT(enPort)) || (!IS_VALID_PIN(enPin)))
    {
        return Error;
    }
    /* 实际配置 */
    /* ... */
    return Ok;
}
```

这解释了为什么 `en_result_t` 只有 `Ok` 和 `Error`——它只反映参数检查是否通过，不反映运行时的复杂状态。

了解这一点有个实际用处：如果你的 `XXX_Init()` 返回 `Error`，问题几乎肯定是**参数填错了**。检查你的枚举值是不是填了不属于这个字段的类型——比如把 `UsartDataBits8`（属于数据位字段）填到了停止位字段上。C 语言的枚举类型检查不严格，这类错误编译器不一定能发现。

## 3.5 DDL_UTILITY 工具箱

3.1 提到的 `DDL_UTILITY_ENABLE` 开关背后，是一个叫作 **DDL_UTILITY** 的模块（源码在 `driver/src/hc32f460_utility.c`）。它和任何具体外设都无关，提供四个"开箱即用"的工具，几乎在每个工程里都会用到：

| 工具 | 函数 | 作用 |
|---|---|---|
| 软件延时 | `Ddl_Delay1ms` / `Ddl_Delay1us` | 粗略的忙等延时 |
| SysTick 时基 | `SysTick_Init` / `SysTick_GetTick` / `SysTick_IncTick` | 全局毫秒时钟，用于非阻塞计时 |
| 断言 | `DDL_ASSERT` | 调试期参数校验 |
| 打印 | `DDL_PrintfInit` / `DDL_Printf` | 通过串口输出调试信息 |

它们之所以放在"配置"这一章，是因为它们是最底层的基础设施：后面每一章（GPIO 闪烁、串口打印、定时器、综合项目）都会反复出现。先把这套工具认全，后面就不会每次遇到一个陌生函数都去翻头文件。

### 3.5.1 软件延时：Ddl_Delay1ms / Ddl_Delay1us

这是最简单的"等一会儿"。源码实现非常直白——靠主频算出循环次数，然后空转：

```c
/* driver/src/hc32f460_utility.c 节选 */
void Ddl_Delay1ms(uint32_t u32Cnt)
{
    volatile uint32_t i;
    uint32_t u32Cyc = SystemCoreClock / 10000ul;   // 主频决定循环次数
    while (u32Cnt-- > 0ul)                          // 每个 ms 空转 u32Cyc 次
    {
        i = u32Cyc;
        while (i-- > 0ul) { ; }
    }
}
```

用法一行就够：

```c
Ddl_Delay1ms(500);   // 粗略等待约 500ms
Ddl_Delay1us(10);    // 粗略等待约 10us
```

**三个必须知道的特性：**

1. **它是阻塞的。** 延时期间 CPU 卡在空循环里，什么别的活都干不了。你不能指望"延时的时候顺手去扫一下按键"。
2. **精度是"近似"（approximate）。** 注释里原话就是 *approximate*。循环次数按主频估算，实际受指令流水线、编译优化影响，误差在百分之几到百分之十几都有可能。`Ddl_Delay1us` 尤其粗糙——高主频下一次函数调用和循环本身的开销就可能吃掉好几个微秒。所以它适合"上电稳定一下""LED 闪一下"这类**不要求精确定时**的场景；精确时序请交给硬件定时器（第 9 章）。
3. **不喂看门狗、且别在中断里用。** 延时越长，期间若开了独立看门狗就可能触发复位；在中断服务函数里调它会拖长中断响应，导致别的中断被饿死。

下面这个基于开发板的最小示例，用 `Ddl_Delay1ms` 让 PA00 上的 LED 以约 1Hz 闪烁（LED 引脚初始化细节见第 7 章，这里先照抄）：

```c
#include "hc32_ddl.h"

int main(void)
{
    /* LED 引脚最小初始化：PA00 推挽输出 */
    stc_port_init_t stcLedInit;
    MEM_ZERO_STRUCT(stcLedInit);
    stcLedInit.enPinMode = Pin_Mode_Out;
    PORT_Init(PortA, Pin00, &stcLedInit);

    while (1)
    {
        PORT_Toggle(PortA, Pin00);   // 翻转 LED（极性无所谓，反正闪烁）
        Ddl_Delay1ms(500);
    }
}
```

### 3.5.2 SysTick 时基：非阻塞的"毫秒时钟"

`Ddl_Delay1ms` 的问题在于"阻塞"。实际项目里你常常需要"等 500ms 后再做某件事"，但**这 500ms 里还要去轮询按键、刷新屏幕、处理通信**。靠忙等延时做不到——它把 CPU 全占了。

DDL_UTILITY 用 Cortex-M 内核自带的 **SysTick** 定时器（不属于任何外设，是内核标配）提供了一个全局毫秒计数器。你随时可以问"现在几点了"，用它算出"过去了多久"，而不必傻等。

核心 API：

```c
en_result_t SysTick_Init(uint32_t u32Freq);  // 初始化，参数 1~1000 是中断频率(Hz)
void       SysTick_IncTick(void);            // 时基自增，必须在 SysTick 中断里调
uint32_t   SysTick_GetTick(void);            // 取当前毫秒计数值
void       SysTick_Delay(uint32_t u32Delay); // 基于时基的忙等（等价于 Ddl_Delay1ms）
void       SysTick_Suspend(void);            // 暂停时基
void       SysTick_Resume(void);             // 恢复时基
```

`SysTick_Init(1000u)` 表示每秒产生 1000 次中断，也就是**每 1ms 走一个 tick**；如果你传 `SysTick_Init(1u)`，就是每 1 秒一个 tick（某些低功耗场合用）。

**最关键的一个坑：DDL 不会替你写 SysTick 中断服务函数。** 时基的累加完全靠你在 `SysTick_Handler` 里手动调用 `SysTick_IncTick()`。忘写的话，`SysTick_GetTick()` 永远返回 0，整个时基是死的。这是开发板 `systick` 例程（`example/.../v2/systick`）的标准写法：

```c
/* 必须自己实现：SysTick 每次中断，让全局时基 +1 */
void SysTick_Handler(void)
{
    SysTick_IncTick();
}
```

> 注意：SysTick 是内核异常，**不经过 INTC，不占用 `Int000`/`Int001` 那些中断槽位**。所以你和后面第 5 章的 PC13 按键中断（`Int000`）、第 9 章的 Timer0（`Int001`）完全不冲突，放心用。

完整的最小可跑示例（基于开发板 `systick` 例程，用非阻塞方式让 PA00 每 500ms 翻转一次）：

```c
#include "hc32_ddl.h"

static uint32_t u32LastTick = 0;

int main(void)
{
    /* LED 引脚初始化（同 3.5.1，PA00 推挽输出） */
    stc_port_init_t stcLedInit;
    MEM_ZERO_STRUCT(stcLedInit);
    stcLedInit.enPinMode = Pin_Mode_Out;
    PORT_Init(PortA, Pin00, &stcLedInit);

    SysTick_Init(1000u);          // 启动 1ms 时基

    while (1)
    {
        uint32_t u32Now = SysTick_GetTick();
        /* 每 500ms 翻转一次；u32Now - u32LastTick 用无符号减法，
           即使 GetTick() 溢出归零也能正确计算间隔 */
        if ((u32Now - u32LastTick) >= 500u)
        {
            u32LastTick = u32Now;
            PORT_Toggle(PortA, Pin00);   // 翻转 LED
        }
        /* 这 500ms 里，循环空转但随时可以插入别的任务：
           读按键、刷屏幕、处理通信……都不会被延时阻塞 */
    }
}

/* SysTick 中断：让时基前进（必须） */
void SysTick_Handler(void)
{
    SysTick_IncTick();
}
```

对比一下两种方式（假设要"每 500ms 干一件事，期间还要扫按键"）：

| | 阻塞延时 `Ddl_Delay1ms` | 非阻塞时基 `SysTick_GetTick` |
|---|---|---|
| 等待期间能否干别的 | 不能（CPU 卡死） | 能（循环里随便加任务） |
| 精度 | 近似、受主频影响 | 由 SysTick 硬件决定，稳定 |
| 额外开销 | 无 | 占用一个 SysTick 中断 |
| 适用 | 简单闪烁、上电延时 | 多任务轮询、状态机、通信超时 |

经验法则：**只要你的 `while(1)` 里还需要做别的事，就用 SysTick 时基，别用 `Ddl_Delay1ms`。**

### 3.5.3 断言：DDL_ASSERT

开发阶段，你写的很多函数需要校验入参。DDL_UTILITY 提供了断言宏：

```c
#ifdef __DEBUG
    #define DDL_ASSERT(x)  ((x) ? (void)0 : Ddl_AssertHandler(__FILE__, __LINE__))
#else
    #define DDL_ASSERT(x)  (void)(0)     // Release 下整体消失，零开销
#endif
```

用法——在自己函数的入口校验参数：

```c
void MyFunc(en_port_t enPort)
{
    DDL_ASSERT(IS_VALID_PORT(enPort));   // 端口非法就卡在断言里
    /* ... 正常逻辑 ... */
}
```

当 `x` 为假（条件不满足），断言会调用 `Ddl_AssertHandler`，打印出**出错的源文件名和行号**，然后进入死循环。调试时程序停在这里，你立刻知道是哪个断言没过、在哪一行。

两个注意点：

- 断言只在定义了 `__DEBUG`（Debug 编译）时有效；切到 Release 后 `DDL_ASSERT` 被编译成空语句，不产生任何代码、不占空间。所以它适合"抓开发期的低级错误"，不适合"处理运行期的正常异常"（那要用返回值 / `if` 判断）。
- 断言失败是**死循环**，不是返回错误。别拿它去判断"用户可能输入非法"这种正常情况。

### 3.5.4 打印：DDL_PrintfInit / DDL_Printf

调试时最直观的手段是把变量通过串口打出来。DDL_UTILITY 把它包成了标准 `printf`：

```c
/* 需要 DDL_PRINT_ENABLE == DDL_ON（默认是 DDL_OFF，要在 ddl_config.h 打开） */
en_result_t UART_PrintfInit(M4_USART_TypeDef *UARTx,
                            uint32_t u32Baudrate,
                            void (*PortInit)(void));   // 第三个参数是"端口初始化回调函数"
#define DDL_PrintfInit   (void)UART_PrintfInit
#define DDL_Printf       (void)printf
```

**第三个参数 `PortInit` 是最容易踩坑的地方。** 它不是一个现成函数，而是**你要自己写的"端口初始化回调"**——`UART_PrintfInit` 内部只负责设置波特率、打开发送（`CR1_f.TE = 1`），**串口引脚的复用和时钟门它一概不管**。它会在初始化时回调你传进去的这个函数，让你把 TX/RX 引脚接到 USART 上。所以调用之前，你必须自己准备好这个函数，并且先打开 USART 的时钟门。

你的开发板用 **USART2，引脚 PA10(RX) / PA15(TX)**（详见第 8 章），对应的回调实现如下（与第 11、14 章一致）：

```c
/* 传给 DDL_PrintfInit 的第三个参数：DDL 初始化串口时会回调它。
   作用：把 PA10 / PA15 复用成 USART2 的 Rx / Tx。
   （GPIO 时钟门一般在系统初始化 BSP_CLK_Init 里统一开，这里不重复开） */
static void Usart2_PortInit(void)
{
    PORT_SetFunc(PortA, Pin10, Func_Usart2_Rx, Disable);
    PORT_SetFunc(PortA, Pin15, Func_Usart2_Tx, Disable);
}
```

完整的打印初始化片段（注意 `PWC_Fcg1PeriphClockCmd` 这一行不能省，否则串口寄存器写了也不生效）：

```c
/* 1. 先开 USART2 外设时钟门（PWC，详见第 4 章） */
PWC_Fcg1PeriphClockCmd(PWC_FCG1_PERIPH_USART2, Enable);

/* 2. 绑定打印口：DDL 会回调 Usart2_PortInit 去配置引脚 */
DDL_PrintfInit(M4_USART2, 115200u, Usart2_PortInit);

/* 3. 之后就能直接用 printf / DDL_Printf 了 */
DDL_Printf("sys tick = %lu\r\n", SysTick_GetTick());   // 等价于 printf
```

两个要点：

- **默认关闭。** `ddl_config.h` 里 `DDL_PRINT_ENABLE` 默认是 `DDL_OFF`。要用打印，先把它改成 `DDL_ON`，否则 `DDL_PrintfInit` / `DDL_Printf` 会被宏替换成空语句——编译不报错，但什么也不输出。
- **`DDL_PrintfInit` 是查询发送**，内部带超时（`m_u32PrintfTimeout = SystemCoreClock / baudrate`），不开启串口中断、不占 INTC 槽位。所以它和你的按键中断、定时器中断都不冲突，用在初始化阶段或低频日志很合适；高频大量输出建议改用中断 / DMA 方式（第 8、10 章）。

### 3.5.5 这一节记住什么

DDL_UTILITY 是横切所有章节的"基础设施"包，四个工具各自解决一类问题：

- **`Ddl_Delay1ms/us`**：粗略忙等延时，简单但阻塞，精度近似，别在中断里用、别指望精确。
- **`SysTick_*` 时基**：提供全局毫秒时钟，支持非阻塞计时；**记得自己写 `SysTick_Handler` 调 `SysTick_IncTick()`**，它走内核异常不占 INTC 槽位。
- **`DDL_ASSERT`**：调试期参数校验，失败打印文件行号并死循环，Release 自动消失。
- **`DDL_PrintfInit/DDL_Printf`**：串口打印，需 `DDL_PRINT_ENABLE` 开启（默认关），查询发送不占中断。

## 3.6 完整的配置流程

把前面几点串起来，使用任何一个 DDL 外设的完整流程是：

```c
/* 1. 定义配置结构体 */
stc_xxx_init_t stcXxxInit;

/* 2. 清零（必须） */
MEM_ZERO_STRUCT(stcXxxInit);

/* 3. 填充字段 */
stcXxxInit.enField1 = Value1;
stcXxxInit.enField2 = Value2;

/* 4. 开外设时钟门 */
PWC_FcgXPeriphClockCmd(PWC_FCGx_PERIPH_XXX, Enable);

/* 5. 配置引脚复用（如果需要） */
PORT_SetFunc(PORT_x, PIN_x, Func_Xxx, Disable);

/* 6. 调用初始化并检查返回值 */
if (Ok != XXX_Init(M4_XXX, &stcXxxInit))
{
    while(1);    /* 失败处理 */
}

/* 7. 使能功能 */
XXX_Cmd(M4_XXX, Enable);
```

第 4、5 步的具体做法在第 6 章展开。这个流程是所有外设章节的基础模板。

## 3.7 小结

四个要点：

**模块开关**。`ddl_config.h` 控制驱动是否参与编译，开关没开函数就不存在。维护一份代表产品能力的配置，而不是每用个例程复制一份。开关之外还要确认 `.c` 文件在工程里。

**配置结构体必须先清零**。局部变量不初始化，未赋值字段是栈上的垃圾值，会导致行为不可预测。`MEM_ZERO_STRUCT` 应该在定义之后立刻调用。

**错误处理简单直接**。`en_result_t` 只有 `Ok` 和 `Error`，返回 `Error` 通常意味着参数填错了，而不是硬件故障。

**DDL_UTILITY 是开箱即用的基础设施**。它提供四类横切工具：软件延时 `Ddl_Delay1ms/us`（阻塞、近似，别在中断里用）、SysTick 毫秒时基（`SysTick_Init` 之后必须自己写 `SysTick_Handler` 调 `SysTick_IncTick`，走内核异常不占 INTC 槽位，是非阻塞计时的首选）、断言 `DDL_ASSERT`（调试期校验、Release 自动消失）、串口打印 `DDL_PrintfInit`（需 `DDL_PRINT_ENABLE` 开启，默认关）。

这一章的内容不涉及具体外设，但会在后面每一章反复出现。下一章讲启动流程和时钟系统——这是另一个"不涉及具体外设但影响所有外设"的主题。
