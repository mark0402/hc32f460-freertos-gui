# 笔记二 · 控制台组件 Console 与分层日志

## 0. 背景

最早串口交互散在三处：`usart.c`（底层收发）、`log.c`（日志）、`shell_cmds.c`（命令实现），三者互相耦合——命令行、日志、硬件收发缠在一起。加一条命令要改注册表、还要管堆内存。

重构后合并成单一组件 `project/source/console.c` + `console.h`，对外只暴露这一个头文件：

- 串口：由 `CONSOLE_USART` 系列宏统一选择，收发 / 初始化都走它；
- 打印：`Console_Print` / `Console_PrintU32`（异步，不阻塞调用方）；
- 日志：`LOG_ERR` / `LOG_WARN` / `LOG_INFO` / `LOG_DEBUG`（分级，异步）；
- 命令：`CONSOLE_CMD_EXPORT(...)` 自动注册，外部模块只包含 `console.h` 即可。

设计上参考了 RT-Thread finsh 的命令自助注册思路（链接段扫描），以及其 shell 的行编辑交互。

### 0.1 为什么单片机格外需要「日志」和「控制台」

PC 程序出问题，你能弹窗、看 traceback、挂 IDE 打断点单步；网页崩了有浏览器控制台、有 Sentry。但单片机的运行环境完全不同，这恰恰让日志和命令行从「锦上添花」变成了「生存必需品」：

**① 单片机是「看不见、摸不着」的**

量产设备装进机箱、接上强电、跑到现场之后，它没有任何显示器、没有窗口、没有图形界面。你唯一能「看穿」它内部状态的窗口，往往就是那一路串口——把日志吐出来，它才对你「可见」。没有这扇窗，设备就是一个黑盒，出事只能靠猜。

**② 在线调试的局限：你插不上调试器**

SWD/JTAG 打断点这套范式，只在实验室、板子连着电脑时成立。而真实世界里大量问题恰恰发生在：

- 设备已经装机、机箱封死，物理上够不到调试口；
- 现场连着强电 / 旋转机构，没法边跑边接仿真器；
- 偶发竞态——那个 bug 只在某两个中断恰好咬合的几微秒窗口出现，你挂上调试器它就消失了（海森堡式 bug）。

这些场景下，「设备自己把发生了什么记下来」是唯一可行的观测手段。日志就是单片机的**黑匣子**。

**③ 日志 = 仪表盘 + 黑匣子 + 听诊器**

- **启动期**：硬件初始化成功了吗？外设探测到了吗？早期日志可见，才能区分「板子根本没上电」和「卡死在某个外设初始化」。`Console_Init()` 在调度器起来前调用，正是为了让这段最关键的启动日志不丢。
- **运行时健康度**：任务看门狗有没有被按时喂？队列有没有溢出？通信丢包率多少？这些靠日志持续吐出，才能判断是否「亚健康」。
- **事后定位**：现场报了故障，你把串口日志拿回来，能看到崩溃前最后几条记录——这就是排障的全部线索。

**④ 但日志本身就是一把双刃剑，逼出「分层 + 异步」设计**

- 同步打印（直接忙等发串口）会拖垮实时性：115200 波特率发 100 字节 ≈ 8.7ms，业务线程卡在那里干等。对电机控制、通信时序是灾难。所以必须把「记录」和「发送」解耦——记录只往队列里塞，由低优先级任务慢慢搬。
- 日志太详尽又会占带宽、占 Flash。所以需要**分级**：开发期开 `DEBUG` 看细节，出厂把 `LOG_LEVEL` 调高到 `INFO`/`WARN`，既保住关键观测，又减固件体积、降运行开销（低于阈值的级别编译期直接消除，零运行时成本）。
- 本组件的 `LOG_*` 宏 + `prv_emit` 队列 + `prv_print_task`，正是这「双刃剑」的答案。

**⑤ 控制台 = 不烧录就能「远程操作」设备**

单片机通常没有「设置」界面。要改个参数（时间、阈值、校准值），传统做法是重烧固件，或堆一堆实体按键 + LCD——既不经济也不可扩展。而一个串口控制台就是运行时的**远程操作台**：

- `gettime` / `settime`：现场校时，改完还能经 `nv_store` 落盘持久化——不用拆机、不用重烧；
- `led on/off/blink`：远程确认板子还活着（心跳灯），或强制点亮做硬件自检；
- `echo` / `clear`：把信息推到屏幕，调试 UI 层；
- 产线 / 工厂校准：通过串口批量下发指令、读回序列号，比人工按键高效且可自动化。

它相当于给现场工程师一个「听诊器 + 操作面板」：设备联网失败？进控制台查一下状态，立刻分清是配置问题还是硬件问题。

**⑥ 把「看不见」变成「看得见、可操作」——本组件的设计目的**

把分散的 `usart` / `log` / `shell` 三件套合成一个组件，终极目标是：**让任何业务模块都能以最低成本获得「被观测」和「被控制」两件事**。

- 命令**自助注册**（finsh 思路）：加一条命令零样板——不碰注册表、不依赖堆。这让「把系统内部状态暴露出来」变成一行宏，暴露得越多，设备越透明、越好维护。
- 单一头文件：业务模块只 `#include "console.h"`，不感知底层是 USART2 还是 DMA，换串口只改一处宏。耦合越低，越鼓励使用，可观测点就越多。

> 一句话总结：**日志解决「设备发生了什么」，控制台解决「能对设备做什么」。两者合在一起，才让一个装在机箱里、连着强电、远在千里之外的单片机，重新变得可被理解、可被干预。**

## 1. 设计要点

### 1.1 串口选择

`console.h` 里一组宏统一描述控制台串口，换串口只改这一处：

```c
#define CONSOLE_USART      M4_USART2        /* 控制台外设 */
#define CONSOLE_BAUDRATE   (115200ul)
#define CONSOLE_USART_CLK  (PWC_FCG1_PERIPH_USART2)
#define CONSOLE_TX_PORT    (PortA)
/* ... RX / 复用 / 中断源必须配套 ... */
```

组件内部按这些宏做 GPIO 复用、时钟使能、中断 / DMA 收发，业务层不碰底层。

> **为什么这样设计**：串口引脚、时钟、中断号在 HC32F460 上和具体外设强绑定，散落在各模块极易配错（漏开时钟、中断源和引脚不匹配）。集中成一组宏后，「换控制台串口」成为单点修改，且强迫时钟 / 引脚 / 复用 / 中断源「配套出现」，从根上消除配置遗漏。

### 1.2 异步打印

打印走**环形队列 + 低优先级任务**：调用方把字符串塞进队列就返回，由后台任务搬去串口。调度器起来之前（`Console_Init` 在 `vTaskStartScheduler()` 之前调用），走**同步直发**兜底，保证早期日志不丢。

收益：业务线程 `printf` 不会卡在串口波特率上；早期启动日志也能正常出。

```c
static void prv_emit(const char *buf, uint16_t len)
{
    if ((s_out_queue == NULL) ||
        (xTaskGetSchedulerState() != taskSCHEDULER_RUNNING))
    {
        prv_send_string_sync(buf);   /* 调度器未起 → 同步兜底 */
        return;
    }
    /* 否则入队，0 超时满则丢弃，绝不阻塞调用方 */
    (void)xQueueSend(s_out_queue, &msg, 0);
}
```

> **为什么必须异步**：见 0.1 ④。单片机实时任务（控制环、通信时序）不能被一个 `printf` 拖住几毫秒。异步把「产生日志」和「搬运日志」两个时间尺度切开——前者在调用方上下文瞬时完成（仅一次 `xQueueSend`），后者在 `tskIDLE_PRIORITY+1` 的低优先级任务里慢慢发，正常空闲。队列满时直接丢弃而非阻塞，更是为了避免日志反向压垮业务（宁可丢日志，不能卡系统）。
>
> **为什么还要同步兜底**：启动早期、调度器尚未运行，队列和打印任务都还不存在。如果日志依赖调度器，那最关键的「上电初始化」日志反而看不到——而这往往正是设备起不来的时候。同步直发让这段黑匣子照样能录制。`TC-BOOT-01` 即验证此路径。

### 1.3 分级日志

```c
#define LOG_ERR(s)   do { if (LOG_LEVEL >= LOG_LEVEL_ERR)   log_printf(LOG_LEVEL_ERR,   s); } while (0)
#define LOG_WARN(s)  do { if (LOG_LEVEL >= LOG_LEVEL_WARN)  log_printf(LOG_LEVEL_WARN,  s); } while (0)
#define LOG_INFO(s)  do { if (LOG_LEVEL >= LOG_LEVEL_INFO)  log_printf(LOG_LEVEL_INFO,  s); } while (0)
#define LOG_DEBUG(s) do { if (LOG_LEVEL >= LOG_LEVEL_DEBUG) log_printf(LOG_LEVEL_DEBUG, s); } while (0)
```

级别由编译期 `LOG_LEVEL` 控制。**低于阈值的级别直接编译为空**，零运行时开销。想关调试日志就把 `LOG_LEVEL` 调高，发布固件可减体积。

每条日志还自动带 `[tick][级别]` 前缀（`log_printf` 内拼装），回看时既能定位发生时刻，也能一眼区分严重程度：

```text
[12345][Error] i2c device not respond
[12350][Warn]  queue full, drop log
[12399][Info]  system ready
```

> **为什么分级是必须的**：
> - 开发阶段你需要 `DEBUG` 级别的逐字节、逐状态细节；但这些信息在出厂固件里既占 Flash 又刷屏、还可能泄露实现细节。
> - 不同严重程度的事件该区别对待：错误必须立刻看到，普通运行信息平时可以忽略。
> - 编译期消除（而非运行时 `if`）意味着关掉的级别连函数调用都不剩，发布固件真正做到「关调试 = 减体积 + 零开销」，不像运行时开关那样留下判断分支。
> - `[tick]` 前缀则让日志自带时间线——没有它，你无法判断两条日志是相隔 1ms 还是 1 小时发生的，事后定位会失焦。

### 1.4 命令自助注册（核心）

参考 RT-Thread finsh 的 `MSH_CMD_EXPORT`：宏把命令描述符放进独立链接段 `ConsoleCmdTab`，`Console_Init()` 时统一扫描注册。

```c
#define CONSOLE_CMD_EXPORT(_name, _desc, _func, _params) \
    const console_cmd_t __console_cmd_##_name CONSOLE_CMD_ATTR = \
        { #_name, _desc, _func, _params }
/* CONSOLE_CMD_ATTR = __attribute__((section("ConsoleCmdTab"), used))  (GCC / Keil AC6) */
```

扫描实现：

- GCC（ld）：由 `hc32f46x_flash.ld` 提供 `__console_cmd_start` / `__console_cmd_end`，遍历该区间；
- Keil（armlink）：自动提供 `ConsoleCmdTab$$Base` / `$$Limit`，无需改 scatter 文件；
- MDK 与 GCC 双工具链都能自动拿到命令表。

**好处**：加命令不需要改任何注册表、不依赖堆；命令元数据随代码编译进固定段，上电扫描一次即可。

> **为什么这比「注册表 + 堆」好得多**（见 0.1 ⑥）：
> - 原方案加一条命令要改一个全局注册表数组，并手动 `malloc` 描述符——既容易漏改、又有堆碎片 / 失败风险，在资源紧张的 MCU 上是隐患。
> - 链接段扫描把命令「注册」动作前移到**编译期 / 链接期**：命令描述符被编译器直接放进一个固定段，上电扫一遍区间就全载入。无需任何运行时注册调用、不碰堆。
> - 更深层的好处是**心理门槛的降低**：业务模块作者只需写一行 `CONSOLE_CMD_EXPORT(...)`，就能把一个新的「可查询 / 可控制」能力挂上去。注册越无痛，开发者越愿意把系统内部状态暴露成命令——设备就越透明、越易维护。这是「自助注册」真正的价值，而不只是省几行代码。

### 1.5 行编辑

交互循环在组件内处理：提示符 `> `、退格、左右光标移动、上下历史（`s_hist`，环形，含 `s_hist_saved` 暂存当前编辑行）、`Ctrl+C` 取消、`ESC` 退出。命令解析出 `argc/argv` 后分发到对应 `func`。

> **为什么行编辑值得做**：一个只能「整行输入、回车才处理」的裸串口，用起来像在打孔纸带——输错一个字符得重来。退格 / 左右光标 / 上下历史这些看似花哨的能力，实际是**把控制台从「能通信」提升到「能日常使用」**的关键：历史记录让你反复敲过的诊断命令一键复用，`Ctrl+C` 让你从错误输入里脱身。否则这个控制台只会被用一次就嫌烦。底层用 `s_esc` 状态机解析 `ESC [ A/B/C/D` 方向键序列，并按 VT100 的 `\r\033[2K` 做整行重绘——这些是「类终端」体验的标准做法。

### 1.6 接收链路的可靠性细节

RX 走「中断 + 环形缓冲 + 信号量」：中断里只把字节塞进 `s_rx_buf` 并 `xSemaphoreGiveFromISR` 通知，交互任务阻塞等信号量再取字节做行编辑——**不轮询、不占 CPU**（`prv_shell_task` 在 `s_rx_sem` 上 `portMAX_DELAY` 阻塞）。

同时做了几个细节防护：

- 环形缓冲满则丢弃新字节（而非覆盖未读数据），避免旧输入被悄悄篡改；
- `prv_send_byte_raw` 自带超时，串口异常（线被拔、对端掉电）时不会把整个系统锁死在忙等里；
- `prv_handle_enter` 吞掉 `\r\n` 中的 `\n`，避免一行命令被当成两条执行；
- 接收错误中断（`prv_err_irq_cb`）清帧错误 / 校验错 / 溢出错标志，保证后续字节正常接收。

> **为什么这些细节不是「过度设计」**：串口是异步、易受干扰的物理链路。现场线缆长、有干扰、对端可能随时热插拔。任何一个「忙等无超时」「覆盖未读数据」「不分 `\r\n`」的疏漏，都会让控制台在真实环境里偶发卡死或串命令——而偶发问题最难复现、最耗排障时间。这套防护让控制台本身成为「最稳的那一路」，关键时刻靠得住。

## 2. 内置命令

`console.c` 末尾用 `CONSOLE_CMD_EXPORT` 注册了 6 条命令，`help` 由框架自动汇总输出：

| 命令 | 参数约束 | 作用 |
|---|---|---|
| `clear` | 0 参数 | 清屏（清 RX 显示行） |
| `led` | 变长（`on`/`off`/`blink`） | 控制 PA00 心跳 LED |
| `echo` | 变长 | 回显文本到屏幕 |
| `gettime` | 0 参数 | 显示当前墙钟 `YYYY-MM-DD HH:MM:SS` |
| `settime` | 至少 2 参数（`YYYY-MM-DD hh:mm:ss`） | 设置 RTC，并立即落盘 `nv_store` |
| `uptime` | 0 参数 | 显示系统运行秒数 |
| `help` | — | 自动列出以上命令及用法 |

> 宏的第四参 `_params`：0 表示固定 0 参，2 表示至少 2 参，`-1` 表示变长（由命令实现自行解析）。

> **这些命令就是「控制台价值」的最小示范**：`settime` 展示了「不重烧固件、现场改配置并持久化」，`led` 展示了「远程硬件自检」，`uptime` 展示了「运行时健康度查询」。它们本身简单，但模式可以无限复制——任何内部状态都能照此暴露成一条命令。

## 3. 怎么加一条命令

三步，零样板：

```c
#include "console.h"

static int prvCmdMy(char *out, size_t len, const char *cmd)
{
    Console_Print("my command run\r\n");
    return 0;
}
CONSOLE_CMD_EXPORT(my, "my: demo command\r\n", prvCmdMy, 0);
```

只 `#include "console.h"`，把该 `.c` 编进工程即可——`Console_Init()` 会自动扫描 `ConsoleCmdTab` 段完成注册，`help` 也会自动带上它。**不需要**改任何注册表、不需要手写初始化调用。

## 4. 一个真实排障场景（日志 + 控制台如何协同）

> 把前面所有设计点串起来，看它们在实际里怎么一起工作。这是理解「为什么需要它俩」最直观的方式。

**场景**：现场一台挂在配电柜里的设备，用户报「时间经常不对，偶尔重启后配置丢失」。你人在办公室，让现场运维接上串口：

1. 上电瞬间，启动期日志经**同步兜底**（`TC-BOOT-01`）已经吐出初始化过程——看到 `[Info] console ready`，确认板子活着、串口通。
2. 敲 `gettime` → 显示 `2026-09-03 03:14:07`，比真实时间慢了几个小时。敲 `settime 2026-09-03 12:00:00` → 经 `AppTime_Set` 更新 RTC，并立刻 `nv_store` 落盘（`TC-DISP-03`）。无需拆机、无需重烧。
3. 敲 `uptime` → 显示 `uptime: 86400 s`，发现设备已连续跑了一天，排除了「频繁重启」。
4. 回看启动日志，发现若干条 `[Warn] nv write busy`，结合 `settime` 才落盘成功，怀疑是上电早期 `nv_store` 队列还没就绪时就有写请求被丢掉——一个靠日志才暴露、靠命令才复现的问题。
5. 中途输错命令 `led blinkk` → 参数校验失败，输出 `usage: led on|off|blink`（`TC-DISP-05`），系统稳稳兜底，没有崩。
6. 按 `↑` 调出历史里刚敲过的 `gettime` 复核，确认时间已校正。

这一整套：日志提供「发生了什么」的线索，控制台提供「我能做什么」的手段。两者缺一个，排障都走不通——没有日志你连「nv 写繁忙」都看不到；没有控制台你只能重烧固件去校时。

## 5. 集成位置

`main.c` 在 `vTaskStartScheduler()` **之前**调用 `Console_Init()`：

- 先完成串口硬件初始化、创建异步输出队列与打印任务、扫描注册全部命令、创建交互任务；
- 调度器起来前的早期日志走同步兜底；调度起来后自动切到异步队列。

## 6. 资源占用

- RAM：约 1.5KB（输出队列 + 交互任务栈 + 行缓冲 / 历史缓冲）；
- CPU：打印任务低优先级，正常空闲；日志低于 `LOG_LEVEL` 的级别编译期消除，零运行时开销。

> **投入产出比**：约 1.5KB RAM 换来的是「设备全程可被观测、可被控制」。对一块 HC32F460（片上 SRAM 以百 KB 计）而言，这是极低的代价换极高的可维护性。也正因为成本可控，才值得在几乎所有项目里默认内置。

## 7. 测试用例推演结果

> 设计期推演（白盒 + 场景），固化「组件对各输入的预期行为」，便于后续回归与移植验证。

| 编号 | 用例 | 设计点 | 过程 / 预期 | 结论 |
|---|---|---|---|---|
| WB-CMDREG-01 | 命令自助注册无注册表 / 无堆 | 链接段扫描 | `Console_Init` 遍历 `ConsoleCmdTab` 段，自动载入 6 条命令；不调用任何手动注册、不分配堆 | 通过（GCC 走 ld `__console_cmd_*`，Keil 走 `$$Base/$$Limit`） |
| TC-BOOT-01 | 上电早期日志可见 | 同步兜底 | `Console_Init` 在调度前调用，启动期 `LOG_*` 经同步直发出串口，不丢 | 通过 |
| TC-DISP-01 | `led on` | 控制外设 | 解析到 `led`+`on`，PA00 置位点亮；`off` 熄灭、`blink` 心跳 | 通过 |
| TC-DISP-02 | `help` | 自动汇总 | 逐条输出 6 命令用法字符串，每条带 `\r\n` 不串行 | 通过（注意：帮助串缺 `\r\n` 会粘成一行，见 `console.c` 注释） |
| TC-DISP-03 | `settime 2026-09-03 12:00:00` | 参数 + 落盘 | 解析 6 字段 → `AppTime_Set()` 更新 RTC → `nv_store` 入队落盘；`gettime` 回读一致 | 通过 |
| TC-DISP-04 | 未知命令 `foo` | 分发兜底 | 扫描命令表无匹配 → 输出 `unknown command: foo` | 通过 |
| TC-DISP-05 | `settime` 缺参数 | 参数校验 | `_params=2`，参数不足 → 输出用法提示，不写 RTC | 通过 |
| TC-DISP-06 | 空行回车 | 空输入 | 行缓冲为空 → 不触发任何命令，仅重绘提示符 | 通过 |
| TC-EDIT-01 | 退格 / 光标 / 历史 | 行编辑 | `Backspace` 删字、左右键移光标、`↑/↓` 调历史（`s_hist_saved` 暂存当前行，再按 `↓` 可回） | 通过 |

| TC-ASYNC-01 | 调度后打印不阻塞 | 队列解耦 | 业务线程 `Console_Print` 仅入队即返回；低优先级任务搬串口，调用方不被波特率阻塞 | 通过 |
